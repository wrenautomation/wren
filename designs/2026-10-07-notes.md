# Notes: docs inside Wren (2026-10-07)

William, 2026-10-07: "for rough notes / disorganized thinking I'm doing it all in google docs right
now. that's a big underrated part of these systems: everything is officialized / formalized so
people end up using their own docs / disorganized way of doing things anyways. so need ways to dump
thoughts into this, store rough thoughts, plans, etc. so everything is truly unified."

Then: "notes need to have version control, all that jazz. notes are essentially just like google
docs but in our system."

## Answer first

- **Notes** is an app in every workspace, Wren's and each client's. A note is a doc: title, rich
  body, nesting, stars, archive. It works for Wren's team and for a client's own people.
- **Google Docs parity, in batches:** versions you can name, compare and restore; live editing
  with cursors; comments and suggestions; sharing by person, team, client or link; outline,
  tables, checklists, images, find and replace, word count, print; Markdown, PDF and .docx out;
  Markdown and .docx in.
- **One source of truth:** each note is a Yjs document stored in Postgres. Every browser, the CLI
  and the live room write Yjs updates; the server merges them, so offline edits and two tabs
  always merge. JSON and plain text are derived on each save for search, links and export.
- **Capture anywhere:** ⌘K "note: …", the N key, the mic in the editor, a phone at 390.
- **Linked:** `@` mentions records and people. Every record page lists the notes that mention it.
- **Agents use it:** `wren notes add|ls|show|search|append` and the portal API. Agent notes say so.
  Ask Claude reads the notes the asker can open.
- **Private by default.** A note is its owner's until shared. Training export is off unless a
  note or its workspace opts in.

## Where it lives

- `packages/notes` (`@wren/notes`): schema, the store, Yjs and text helpers, sharing, search,
  `NotesConsole` (the portal service), records, the live room's logic.
- Web: `apps/portal/web/src/modules/notes/`. Editor: Tiptap 3 (ProseMirror) with its Yjs binding.
  Nothing in the portal had a rich text editor. Tiptap is maintained, React 19 ready, has
  markdown input rules, tables, task lists, mentions, a suggestion API for the slash menu, and
  first party Yjs extensions (collaboration, carets).
- Tables live in every database (one schema everywhere). A client's notes stay in its own
  database. Wren's notes are in main.

## Data

| Table | Holds |
|---|---|

| `note_shares` | note, who (an email, `team`, `client:<id>`), role (`view`, `comment`, `edit`), by, at |
| `note_stars` | note, email, at: Starred is per person |
| `note_seen` | note, email, at: Recent, and what changed since you looked |
| `note_updates` | every Yjs update as it arrived: note, update, by, at. Append only |
| `note_versions` | note, number, kind (`auto`, `named`, `restore`, `import`), name, title, body, text, authors, started_at, at, restored_from |
| `note_links` | note, target (`<record type>:<id>`, `note:<id>`, `person:<email>`), label. Rebuilt from the body on each save |
| `note_comments` | thread, note, parent, quote, body, mentions, by, at, edited_at, resolved_at, resolved_by |
| `note_mentions` | who was mentioned where (note or comment), by, at, seen_at |
| `notes_settings` | one row: the workspace's training opt-in |

## Saving and versions

- The browser keeps the note's Yjs doc in IndexedDB, so a draft survives a closed tab or no
  network. It sends what the server lacks (`notes/sync`: update plus state vector) and applies what
  comes back.
- The server locks the row, merges, appends the update to `note_updates`, and derives body JSON
  (`yXmlFragmentToProsemirrorJSON`, no schema needed), text, title fallback and links.
- A version is one person's sitting: the newest `auto` version is updated in place while the same
  person keeps editing within 10 minutes; anyone else, or a longer gap, starts a new one. Named,
  restored and imported versions always start a new one. With `note_updates` kept whole, any state in between can be rebuilt.
- Restore writes the old body into the live doc as one change and saves a `restore` version.
  Nothing rewinds.
- Compare: any two versions, word level, colored by author. Each step between them is replayed so
  every inserted word is credited to the session that wrote it, and every removed word to the one
  that removed it.
- Server side writes (CLI add and append, quick capture, restore, import) build Yjs nodes from the
  editor JSON with our own converter (`jsonToY`), tested against y-prosemirror's reader.

## Sharing and access

- Routes need `read` (open, list, search), `comment` (comment) and `act` (create, edit) on the app
  `notes`, through the existing guard. Scoped grants on `notes` work as they do anywhere.
- A note's own role for a viewer is the best of: owner; a share to their email; `team` for Wren's
  team; `client:<id>` for that client's people (a Wren note shared to a client); the general
  access when they are in the workspace. Wren's workspace is Wren's team; a client's is its people.
- What they can do is the lower of that role and their app permission: view needs `read`,
  comment needs `comment`, edit needs `act`. Owner adds sharing, transfer, delete.
- Private means private: an admin can't open someone's private note in the portal, and View as
  shows only what the workspace shares. The CLI holds the database and acts as admin, as
  everywhere.
- A new child note copies its parent's sharing. Nothing inherits after that.

## Links and backlinks

- `@` in the editor searches people, clients and notes (batch 1); companies, drafts, workflows,
  templates and SOPs follow. A mention stores the record type and id; its link is the record's
  page.
- A plain link to another note counts too. Other record pages count through `@` only.
- Each record page gets a Notes section: the notes that link to it and that the viewer can open.

## Search

Postgres full text: `websearch_to_tsquery('english', q)` over `search`, ranked, with a
`ts_headline` excerpt. A title prefix match catches short words. Archived notes only when asked.

## Editor

Markdown shortcuts, headings, lists, checklists, quotes, code blocks, dividers, tables, links,
images pasted or dropped (into the files bucket, signed per note), `@` mentions, a `/` menu, an
outline from the headings, find and replace, word count, print, undo that knows whose edit it was.
The mic is on Quick note (`DictateField`); a mic in the editor itself comes with batch 4.

## Live editing (batch 2, built)

- A Durable Object per note on the portal Worker (`NoteRoom`, `apps/portal/src/live.ts`) runs the
  room (`packages/notes/src/room.ts`) over a WebSocket at `/api/notes/live/<id>`. The token rides
  in `Sec-WebSocket-Protocol` (`wren-notes, <jwt>`); the Origin must be the page's own host; a
  client's host pins the client. No live on the demo; without the binding the page syncs over HTTP.
- The room never decides access. On join and every 15s it calls `notes/sync` as each person;
  the answer carries their role, so a share change reaches open pages within a poll. A 404 puts
  them out; a role change sends a `role` frame.
- Editors' updates go out at once and save to `notes/sync` after 1.5s. A commenter's go out only
  after the server takes them. A viewer's are refused.
- Cursors: awareness, stamped with the signed-in email by the room. A peer can't speak for
  another's cursor.
- The last one to leave flushes, with one retry. The page keeps its HTTP sync as the fallback.
- Gap, accepted: a revoked editor's edits in the 15s before the next poll may already be relayed.
- Deploy: `wrangler.toml` adds the `NOTE_ROOM` binding and migration `v1` (`new_sqlite_classes`).
- The local preview runs the same room in Node (`ws`); `?as=` or a `preview_as` cookie is a
  second person.

## Comments, suggestions, mentions (batch 2, built)

- A comment anchors to Yjs relative positions (`note_comments.anchor`), so it moves with the
  text and survives other people's edits. Highlights are decorations, never marks in the doc.
  Threads have replies, edit and delete (author; the owner can delete), resolve and reopen; a
  reply reopens. Comment needs the `comment` role.
- Suggest mode: `suggestAdd` and `suggestDel` marks with author and minute. Inline text only;
  new paragraphs and formatting are refused with a toast. A commenter is always in suggest mode,
  and the server takes their change only when the body without their own suggestions is
  unchanged (`onlySuggests`). Editors accept or reject one or all; a commenter can take back
  their own.
- `@person` in a comment or the body writes `note_mentions`. The person sees it under Notes →
  Mentions, with an unseen count on the tab; opening the note marks it seen. Mentions show only
  for notes they can open: a mention never shares. The `@` list says "Can't open it".
- Not built: a Mentions tile in Wren's Inbox (records are views, not per person) and email for a
  mention.

## Import and export (batch 3)

- Out: Markdown, PDF (print), .docx (`docx`).
- In: Markdown and .docx (`mammoth` to HTML, then the editor's parser), as a new note.
- Google Drive: "In development". It needs William's Google consent, so no OAuth flow is built.

## Capture

- ⌘K: typing "note: …" offers "Add to your notes". It appends a timestamped line to the person's
  Dump note in that workspace, made on first use.
- N anywhere outside a text box opens Quick note: a box with the mic. ⌘Enter or "Add to Dump"
  saves to Dump; "Make it a note" opens it as a new note.
- Phone: the list and the editor work at 390. The toolbar scrolls sideways; the outline hides.

## Turn rough into real

Select text, then: make a draft (Marketing draft, "In development" until its route takes a body),
make an SOP ("In development"), make a task ("In development": there are no tasks). Each says so
in the menu instead of hiding.

## Agents

- CLI: `wren notes add|ls|show|search|append [--client id] [--as email]`. `--as` reads as that
  person; without it the CLI sees everything, as it does for every table. `add` and `append` from
  the CLI write as `agent:claude` (or `--agent <name>`), via `agent`, shared with the workspace.
- Ask Claude: the console's `question` adds up to 5 matching notes the asker can open (title,
  excerpt, link) to the question it sends.

## Training

`wren train export --notes` adds `wren.note/1` lines: notes with `train` on, or every note in a
workspace whose `notes_settings.train` is on. Default off. The toggle is in the note's menu and in
Notes settings. Each line has the title, text, versions with authors, and whether a person or an
agent wrote it.

## Decision log

- 2026-10-07: batch 2. The room relays and asks `notes/sync` for each person's role, so access
  stays in one place. Comment anchors are Yjs relative positions in the database, not marks, so
  a commenter never edits the doc to comment. Suggest mode is inline only: block changes can't be
  checked as suggestions, so they are refused instead of slipping through as edits.
- 2026-10-07: written. Yjs from batch 1: it makes offline merges and two-tab edits correct before
  the live room exists, and the room is then a relay, not a rewrite. Postgres keeps the doc, the
  derived JSON and text, so search, export and the CLI never need a browser. Every update kept;
  versions are sessions over them, so the timeline reads like Docs and nothing is lost. Tiptap over
  Lexical: first party Yjs, tables and mentions, and a JSON shape y-prosemirror reads without a
  schema. Stars per person instead of a shared pin. A client's notes in its own database; a Wren
  note shared to a client is read from main. Private notes stay private from admins in the portal.
