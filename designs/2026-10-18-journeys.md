# Journeys: offers, terms, funnels, journeys, deals on the spine

Living doc. Started 2026-10-18. Detailed design spawned by `2026-10-18-pipeline-first.md`. No amounts or names here (public repo); amounts live in the private `sops/` repo and reach the DB only through the CLI.

## Summary

- One new package, `@wren/pipeline`, and one new Postgres schema, `pipeline`, in every workspace DB (main for Wren, `wren_client_<id>` for a client). It sits beside `profiles` and `events`, so a transition, its spine event and its person share one DB and one transaction.
- Version tables are append only (a `never_edited` trigger, as `books` does). No version library: drizzle rows plus the `template_versions` pattern plus the audit triggers cover it.
- A funnel version is a generated spine workflow, `funnel.<id>.v<n>`, as `cadenceWorkflow` makes one from data. A transition is a spine arrival at a stage node with subject `journey:<uuid>`. `uq_events_entry` gives "once per stage per journey" for free. No second event system.
- No XState. The verdict and the reasons are in "Framework vet".
- `@wren/deals` folds into journeys and then goes. Prod holds 0 deals, 0 moves and 0 saves that use `trigger.deal` (read on 2026-10-18), so the fold moves no data today. A guard migration refuses the drop if that changes.

## The objects

```
Offer ──< OfferVersion           (code registry, synced by hash)
  └──< TermsVersion              (per offer and plan, effective date)
Funnel ──< FunnelVersion         (ordered stages, entries, one sale stage)
Profile ──< Journey >── FunnelVersion
                └── transitions = spine events (cause: touch, payment, booking, reply, ...)
Journey ──○ Deal >── OfferVersion, TermsVersion
                └── schedule (derived), collected (from payment events)
```

### Offer version

- Source stays code: `packages/offers` (`OFFERS`, `defineOffer`). The DB keeps each published shape.
- `pipeline.offer_versions`: `offer` (registry id), `number` (1, 2, ... per offer), `hash` (sha256 of the canonical `Offer` JSON), `body` (the `Offer`), `why`, `created_at`, `created_by`. Unique `(offer, number)`. The sync compares a new hash only with the newest version, so a change back to an older shape is the next number.
- ICP lives on the offer, so on its version: `Offer.icp?: Icp` in `@wren/offers`. `Icp`: `who` (one line), and optional `industries`, `sizes` (headcount bands), `roles`, `regions`, `must` (plain rules a checker runs), `not` (rules that exclude). `sourced` entries and `research` steps read it from the journey's offer version.
- `wren offers sync` adds a row when the hash of a registry entry moves. The deploy runs the same sync after migrations, beside `wren templates sync` (a miss logs, never blocks). A client's own offers (later) are rows with no registry entry; their source is the row.

### Terms version

- Payment is part of the offer. A terms version is one plan of one offer from one date.
- `pipeline.terms_versions`: `id`, `offer`, `plan` (slug: `standard`, `flat`, `partner-<n>`), `number` (per offer and plan), `effective_from` (date), `body` (`Terms`), `why`, `created_at`, `created_by`. Unique `(offer, plan, number)`.
- `Terms` moves from `@wren/delivery` to `@wren/offers` (the leaf) and grows four optional fields. Old agreement rows still parse.
  - `shareBps`: a revenue share, in basis points.
  - `floorCents`: the least a period bills when a share is in play.
  - `installments`: `{ count, everyDays }` for a setup split in parts.
  - `trialDays`: days before the first bill.
- A change is a new row with a later `effective_from`. A row never changes. The live version of a plan on a date: the highest `number` with `effective_from <= date`.
- `termsFor(offer, over, flat)` in `delivery/src/index.ts` becomes a read of the live terms version. `delivery.agreements` keeps its frozen `terms` copy and gains `terms_version` (nullable for old rows).
- `scheduleOf(terms, signedAt, until?)`: pure. Returns the dated lines a deal implies: setup (or its installments), monthly, per-unit (with the cap), share (no amount: "on reported revenue", floor shown). No row stores the schedule.

### Funnel and funnel version

- `pipeline.funnels`: head. `id` (slug), `name`, `status` (`live` | `off`), `created_at`. `off` stops new journeys. Open journeys still move.
- `pipeline.funnel_versions`: `funnel`, `number`, `body`, `why`, `created_at`, `created_by`. Unique `(funnel, number)`.
- `body` (`FunnelBody`, type in `@wren/pipeline`):

```ts
interface FunnelBody {
  name: string;
  offer: string;                 // registry id the sale stage sells
  stages: Stage[];               // ordered; index = order
  entries: Entry[];              // ordered; order = priority (first match wins)
}
interface Stage {
  key: string;                   // /^[a-z][a-z0-9_]*$/, the spine node id rule
  label: string;
  sale?: true;                   // exactly one stage: reaching it makes the Deal
  on: Advance[];                 // what moves a journey to this stage
  research?: "none" | "light" | "full";  // enrichment on arrival; default none
}
interface Advance {
  trigger: string;               // a trigger component id: trigger.booking, trigger.touch, ...
  with?: Record<string, string | number>;   // that trigger's settings, as a node's `with`
}
interface Entry {
  id: string;                    // youtube, linkedin, ads, referral, ...
  kind: "organic" | "outbound" | "ads" | "referral" | "funnel" | "sourced" | "group" | "manual";
  channel?: string;              // platform or channel the cause must come from
  campaign?: string;             // ads campaign id or `/go/` campaign
  funnel?: { id: string; at?: string }; // kind funnel: that funnel's stage, default its sale stage
  source?: string;               // kind sourced: the research list or discovery run that feeds it
  group?: string;                // kind group: the saved query whose new members open journeys
  to?: string;                   // the stage a journey opens at; default the first
}
```

- Entry kinds `sourced` and `group`:
  - `sourced`: people from ICP-matched lists (`@wren/research` discovery, studies, lead sheets). A person added to the named list opens a journey. The list's match is checked against the offer version's `icp`.
  - `group`: a saved query over people and journeys, live. A person who enters the group opens a journey. Today's segments (`trigger.segment`, `entered`) cover people; the saved-query table over people and journeys is a later brief (bead `wa-8pi.8`).
- `research` per stage: an enrichment step that runs when a journey arrives at the stage. `light`: cheap reads (address check, role, firm basics). `full`: the dossier (`@wren/research` `dossier.ts`). Both read the offer version's `icp`. J1 and J3 only carry the field; J4 wires the step.
- Validation (`checkFunnel(prev, next)`, pure):
  - Keys unique and valid. Exactly one `sale` stage. Every `Advance.trigger` is a known trigger.
  - Append only: `next.stages` starts with `prev.stages`, key for key, in order. Labels and `on` rules may change. A key never goes, moves or gets renamed.
  - `offer` never changes across versions. A new offer is a new funnel.
  - A `funnel` entry names a funnel and stage that exist. Composition makes no cycle (A feeds B feeds A is refused).

### Journey

- `pipeline.journeys`:
  - `id` uuid, `profile_id` (FK `profiles.id`), `funnel`, `version` (the funnel version number it is on now).
  - `stage` (key), `status` (`open` | `done` | `dropped`), `drop_reason` (text, null).
  - `entry` (entry id), `entry_ref` (jsonb: the cause that opened it: touch id, campaign, `/go/` path, prior journey id).
  - `opened_at`, `moved_at`, `closed_at`, `legacy_deal` (integer, null; set only by the fold).
  - Index `(profile_id, funnel, status)`. Partial unique `(profile_id, funnel) WHERE status = 'open'`: one open journey per person per funnel. A person can hold journeys in many funnels at once.
- The row is a cache. The truth is the spine events with subject `journey:<id>`. `wren journeys rebuild <id>` recomputes the row from them.
- `done`: the journey reached the last stage. A journey ends there and never reopens. A person who comes back opens a new journey.

### Deal

- `pipeline.deals`:
  - `id` uuid, `journey` (FK, unique: one deal per journey), `profile_id`, `offer`, `offer_version` (number), `terms_version` (FK, null until signed terms are known).
  - `signed_at`, `ends_at`, `status` (`open` | `won` | `lost` | `ended`), `collected_cents` (bigint, default 0), `currency`.
  - `engagement_id` (Wren's own deals: the `delivery.engagements` row; null in client DBs).
- Made by the `journey.stage` step when a journey reaches the funnel's `sale` stage, with the offer's live version and, if one exists, the plan's live terms version. `wren deals sign <deal> --plan <plan>` sets terms later.
- `collected_cents` is a fold of payment events about the deal (see "Causes"). Never typed by hand.
- `won`/`lost` from today's `@wren/deals` map to: `won` = reached the sale stage; `lost` = journey dropped before it.

## Journeys on the spine

### The generated workflow

`funnelWorkflow(funnel, version): Workflow` (pure, in `@wren/pipeline`, the way `cadenceWorkflow` works). For each stage `k`:

| Node | Uses | Does |
|---|---|---|
| `t_<k>_<i>` | the `Advance.trigger` | hears `Spine/fire` facts with its `with`; output wired to `m_<k>` |
| `m_<k>` | `journey.move` (`with: { to: k }`) | maps a cause to journeys and moves them; output `moved` wired to `s_<k>.in` |
| `s_<k>` | `journey.stage` (`with: { stage: k }`) | the stage arrival; fires `trigger.journey`; makes the deal at the sale stage |

- Workflow inputs `in.<k>` are wired to `m_<k>`. Manual moves, the fold and imports enter there with `Spine/emit`.
- Entries of kind `funnel` become a `trigger.journey` node (`with: { funnel, stage, on: "entered" }`) wired to the `to` stage's move node. Composition is a wire in B's version body. A's version does not know B.
- Workflow `for` is `wren` in main and `client` in a client DB. `stage` (the workflow's own field) is `follow`. Port kind: new event kind `journey` in `EVENT_KINDS`.
- `flowsFor` and `walkFor` in `spine.ts` add the funnel workflows of the workspace: `SpineDeps.funnels(client)` reads `pipeline.funnel_versions` (journaled with `ctx.run`, as saves are). Only versions that are the newest or still hold open journeys are listed.
- The version is in the workflow id, so no `events.version` pin is needed for funnels.
- `spine_executions` gets a title branch for `journey:` subjects (person name, funnel, stage).

### `journey.move` step

Input: a cause event (any subject). Output: zero or more `moved` events, each with subject `journey:<id>`. Steps:

1. Find the person: `personOf(event)` reads the keys on the event data (`profile`, email, phone, visitor, `handle:<platform>`) and calls `profileOf`. No person: no output; the arrival stays as the record.
2. Find the journey: the person's open journey in this funnel on this version. None:
   - If the target stage is an entry stage (`entries[].to`, default the first stage), this workflow is the funnel's newest version and the funnel is `live`: open one. `entryOf(body, cause)` picks the entry (first in priority order whose `kind`, `channel` and `campaign` match; else the person's first touch; else `manual`).
   - Else: no output.
3. Guard: `nextStage(stages, from, to)` (pure). Forward only. Returns `{ to, skipped[] }` or `null` (same or earlier stage, or journey closed).
4. Write under `SELECT ... FOR UPDATE` on the journey row: `stage`, `moved_at`, `status` (`done` at the last stage). A repeat is a no-op: the arrival key and the guard both refuse it.
5. Emit `moved` with data `{ journey, profile, funnel, version, from, to, skipped, cause }`.
   - `cause`: `{ kind: "touch" | "payment" | "booking" | "reply" | "document" | "form" | "funnel" | "manual" | "import" | "version", ref, at }`. `ref` is the cause's own id (touch id, pay link id, booking uid, invoice number, prior journey id).

The arrival at `s_<k>.in` keyed by `journey:<id>` is the transition. One row per stage per journey. Skipped stages get no arrival; they are listed in `data.skipped`.

### `journey.stage` step

1. Write a `profile_events` row (kind `journey`) so the person timeline shows the move.
2. `Spine/fire` with facts `{ trigger: "trigger.journey", funnel, stage, change: "entered" }` (and `"skipped"` once per skipped stage, so a composed funnel keyed to a skipped stage still opens). Other workflows hear it. This is how funnel B opens from funnel A.
3. At the sale stage: insert the deal (`ON CONFLICT (journey) DO NOTHING`).
4. Output nothing. A stage node keeps the arrival and stops.

### Drop

`Journeys/drop { journey, reason }` sets `status = dropped` and emits at a `dropped` node of the workflow (part `journey.stage` with `with: { stage: "dropped" }`), so a drop is an event too. `trigger.journey` fires with `change: "dropped"`.

### New version, same journeys

- Append stage `upsell` to funnel `organic`: version 2. `wren funnels append` writes it.
- Open journeys on version 1 move to version 2 with the same `stage`. Each gets a spine event at `funnel.organic.v2` node `s_<stage>` with cause `{ kind: "version", ref: "1" }`. Their position does not change.
- Version 1 leaves `flowsFor` when it holds no open journey.
- This is open decision 2.

### Manual and agent moves

`Journeys` Restate service in `apps/worker`: `open`, `move`, `drop`, `rebuild`. `open` and `move` call `Spine/emit` at `in.<stage>` of the funnel's newest workflow with cause `manual` and `by` = the operator. Every path goes through `journey.move`. No second write path.

## Causes: what fires today, what is new

| Cause | Today | Change |
|---|---|---|
| reply (email, text) | `trigger.reply` via `Spine/fire` | none |
| booking | `trigger.booking` (`booked`, `cancelled`) | none |
| pay link (client's buyer) | `trigger.payment` (`paid`, `refunded`, `failed`), once via `told` | add `source: "pay_link"` and the link id to the event data |
| Wren invoice (Wise) | `markInvoice` and `BillingWatch` fire nothing | fire `trigger.payment` with `source: "invoice"`; `PayChange` adds `invoiced` and `late` |
| document | `trigger.document` (`signed`, ...) | none |
| form | `trigger.form` | none |
| touch (follow, comment, DM, reply on socials) | `recordTouch` writes `touches`; no spine fire | new `trigger.touch` (see below) |
| journey (composition) | none | new `trigger.journey` |
| deal | `trigger.deal` | retired with `@wren/deals` (0 saves use it) |

- `trigger.touch`: settings `kind`, `direction`, `platform`. `recordTouch` has many writers outside Restate, so the fire comes from a tail loop, not the writers: `TouchFeed` (a loop object, `map/objects/platform/loop-object.md`) reads `touches` past its cursor every minute, per workspace, and calls `Spine/fire` once per new touch with subject `touch:<id>`. The cursor is in loop state. A missed tick catches up on the next.
- `collected_cents`: `journey.stage` does not do it. A `pipeline.collect` step on a code workflow `pipeline.money` (in every workspace) hears `trigger.payment` and adds or takes back the amount on the deal the payment names (`deal` on the pay link or invoice; else the person's newest open deal for that offer). Refunds subtract. The same arrival key makes it once per payment change.
- Profile merges: `mergeProfiles` (core/profiles.ts) also moves `pipeline.journeys.profile_id` and `pipeline.deals.profile_id`. If both profiles hold an open journey in the same funnel, the one at the later stage stays open and the other is dropped with reason `merged`.

## Attribution

- A journey holds one entry: the one that opened it. `entry_ref` holds the proof.
- `sourced` and `group` entries: the list or group is the proof (`entry_ref`: list id or group id, and the row that added the person).
- `entryOf` order: the cause itself (a LinkedIn DM touch opens entry `linkedin`), then the person's first touch (forms already keep first and last touch; lander `wv` cookie; `/go/<channel>/<campaign>/<content>`), then `manual`.
- A composed journey's entry is `{ kind: "funnel" }` with the prior journey id. Numbers can walk back to the first funnel's entry.
- `delivery.engagements.source_channel` and `source_campaign` are filled from the deal's journey entry when a deal makes an engagement.

## Numbers

Views in schema `pipeline`, over `events WHERE workflow LIKE 'funnel.%'` and the `pipeline` tables:

- `pipeline.stage_counts`: per funnel, version, stage, day: journeys entered, journeys skipped past.
- `pipeline.stage_flow`: per funnel and stage pair: conversion (reached next / reached this), median time in stage (window over each journey's events).
- `pipeline.entry_numbers`: per funnel and entry: journeys opened, deals, collected, cost. Cost = `ad_days.spend` for `ads` entries joined on `campaign`; null for organic (no cost model yet).
- `pipeline.offer_numbers`: per offer: deals, collected, open schedule (from `scheduleOf`, in TS, not SQL).

Record `pipeline.number` reads these. No new table. The data lake picks the tables up in its nightly sync like any other.

## Folding `@wren/deals`

Prod on 2026-10-18: `deal_pipelines` 1 (owner null, the default "Sales"), `deals` 0, `deal_moves` 0, workflow saves that use `trigger.deal` 0.

1. `wren pipeline fold-deals` (TS, idempotent, per owner):
   - Each `deal_pipelines` row with custom stages becomes a funnel, version 1: `open` stages in order, the first `won` stage as `sale`, `lost` stages as drop reasons. The default pipeline maps to nothing.

   - Each `deal_moves` row becomes a spine event at `s_<to>` with cause `import`, `by = 'fold'`, `sent = '{}'`. Inserted direct: no step runs, so history fires no triggers.
   - Deal `value_cents` goes to the journey's deal row as an `open` deal with no terms version.
2. Guard migration, then drop: `DO $$ ... RAISE EXCEPTION` if any `deals` row has no journey with that `legacy_deal`, or any `workflow_saves` edits name `trigger.deal`. Then `DROP` the three tables.
3. Code: remove `packages/deals`, `trigger.deal` (logic.ts, editor.tsx), `deals.board`, `dealRecordFor`, `makeDealsConsole`. The portal's `modules/deals` (board, pipelines) re-points at `pipeline.journey` and `pipeline.funnel`: one board per funnel, a column per stage. ## Client zero (Wren on these objects)

Shape only. Offer id, plan amounts and partner people come from a private seed file (`sops/pipeline/client-zero.json`), loaded with `wren pipeline seed`.

- Offer: one registry offer (the seed names it). Its `standard` plan terms come from the catalog `Price`; each partner's plan is its own terms version.
- Funnel `organic` (live). Entries in priority order: `youtube`, `linkedin`, `reddit`, `instagram`, `facebook` (kind `organic`, channel = platform). Stages: `engaged` (their touch: comment, reply, follow), `talking` (DM either way, reply), `call_booked` (booking booked), `call_held` (booking time passed, not cancelled: manual until a calendar trigger exists), `signed` (`sale`; document signed), `paying` (payment paid).
- Funnel `linkedin-dm` (live). Entry `linkedin` (kind `outbound`). Stages: `messaged` (our DM touch), `replied` (their DM touch), `call_booked`, `call_held`, `signed` (`sale`), `paying`.
- Funnel `ads` (off). Entry `ads` (kind `ads`, campaign from the seed). Stages: `lead` (form), `call_booked`, `call_held`, `signed` (`sale`), `paying`.
- Partners: one journey each, opened with `wren journeys open ... --at signed` (cause `manual`, an operator), and a deal signed on that partner's plan. Each deal links its existing `delivery.engagements` row.
- Any step in these funnels that needs William for more than writing or a sales call is a bug. `call_held` is the known gap.

## Framework vet

**XState v5: do not adopt.** It is MIT, vetted and maintained. It does not fit here:

- A funnel version is a total order with one guard: a move goes to a later stage. That is `nextStage`, about 30 lines, pure, tested like `payments/src/states.ts` `step()`.
- What XState gives past that (hierarchy, parallel states, delayed events, actors) the spine and Restate give already, with durability: waits, delays, retries, idempotent arrivals, a row per event, replay, the editor.
- XState does not persist. We would store its snapshot beside the journey row and the events: a second source of truth.
- Versioned machines in XState mean "keep old machine code". We get that from data: each version is a row and a generated workflow.
- Revisit if one stage needs parallel or nested sub-states (an onboarding checklist inside `signed`). Then a statechart could run inside one stage step. Not before.

**Versioning: no library.** drizzle tables plus three patterns already in the repo:

- `template_versions`: a number per head, a hash, append rows.
- `workflow_saves`: append rows, the newest is live.
- `books.never_edited`: a `BEFORE UPDATE OR DELETE` trigger that refuses edits.
- The audit triggers (`packages/db/src/audit/install.ts`) log every write; the `pipeline` version and deal tables go in the `money` area.

**Spine: yes, as is**, with three additions: funnel workflows in `flowsFor`, event kind `journey`, and the `journey:` title branch.

## Open decisions

1. **Where journeys live.** Chosen: the workspace DB (main for Wren, the client's DB for a client), beside `profiles` and `events`. Today's `deals` and `pay_links` are in main with an owner column. The workspace DB gives one transaction for transition, event and person, and no `owner` filter on every read. Cost: cross-client numbers need a query per DB (the lake already does this).
2. **Open journeys on a new version.** Chosen: carry them to the newest version (same stage, a `version` event). Option: pin each journey to its version for life. Carry keeps Numbers and the board on one version; pin keeps history plain.
3. **Negotiated terms.** Chosen: named plans per offer (`partner-<n>`), each a terms version, amounts loaded from `sops/`. Option: a private terms version per deal with no plan. Plans let two partners share terms and let Numbers group by plan; per-deal is simpler when every deal differs.

Smaller calls, made here, open to change: `trigger.touch` by tail loop (not by every writer); `PayChange` grows `invoiced` and `late`; `call_held` is manual until a calendar trigger exists; organic entries have no cost.
