# Starling: the marketing product

2026-11-02. William: put all the code for posting, outbound and multi-channel content together as one named product. Name: Starling. Board: devboard project "Marketing product". Campaigns: `designs/2026-11-02-campaigns.md`.

## Target

One product folder, `packages/starling/`, in two sides on one shared base. Each part stays its own package. Campaigns sit above both sides.

| Side | What | They or we |
|---|---|---|
| Inbound organic | our posts, video (studio), newsletters, lead magnets, search (SEO, AI answers) | they come to us |
| Outbound targeted | comments on their posts, likes, follows, invites, DMs, cold email, cold SMS | we go to them |
| Shared base | the channel contract, one adapter per platform (email and SMS plumbing too) | |

Out of Starling:
- autobrowse: the hands (browser and API calls, caps, proof). It stays in its own repo, behind the Restate `sites` seam.
- `SiteClient`, `SiteCallError`, `isRefusal` and the `sites` box: research, learn, reactivation, watch, email and SMS use them. They stay in core.
- Touches (`core/src/touches.ts`): journeys and the CRM read them. They stay in core.
- Client SMS products (speed to lead, missed calls, review asks, reminders): delivery work, not marketing.

## Options

| | How | For | Against |
|---|---|---|---|
| A. One package `@wren/starling` | Merge all | One import | ~90k lines in one package; slow typecheck; kestrel's import map loses its edges; an adapter can reach anything |
| **B. One folder of packages (chosen)** | `packages/starling/*` | One name and place; package edges stay | A large move; peers editing these files get conflicts |
| C. Map hub only | A hub card | No risk | No name; code stays spread |

Ranked by: clear edges between parts, then one place to look, then move risk.

## Phase 1: the move (pure)

No body changes. Same Restate service names, DB schemas, env names and table names. In-flight invocations stay pinned to their deployment, and the new deployment serves the same service names, so nothing breaks.

A file stays when research, learn, reactivation, watch, email or SMS import it. The import graph decides, file by file, at move time.

Steps:
1. Wait for `peers status` to show no uncommitted peer hunks in the moving folders.
2. `git mv` each folder. Rename each package. Rewrite imports with one script, and keep the script in the commit message.
3. Update: `pnpm-workspace.yaml` (add `packages/starling/*`, `packages/starling/channels/*`), `knip.json`, `deploy/scripts/deploy-vps.sh`, the lockfile (`pnpm install`).
4. Fix the map cards that cite moved paths (~50 files in `map/objects`, `map/processes`) with a sed of old path → new path. Run `_meta/build.sh`.
5. Run `kestrel gen`. The map diff must be renames only. William approves it (`kestrel approve` is his).
6. Run the full gate once. Push with `scripts/push.sh`.

Importers today (files outside the package): content 44, outreach 53, studio 28, channel-email 89, channel-meta 6, channel-search 6, channel-reddit 12, the other four 1 to 2 each, `@wren/core/content` contract users ~120.

Done when: the folders are moved, the gate passes, the deploy is green, no invocation fails, and the map diff shows renames only.

### Phase 2 plan (board "Marketing product", 2026-11-02)

## Open

Who made the first touch decides the first steps and some rules: caps, consent (cold mail and text law, Meta's 24 h window), approval, and which campaign gets the credit. After the first answer, every thread is the same: turns on one channel. So a thread keeps its origin as fields (`opened_by`: us or them; `from`: our post, our comment, our DM, their DM, cold mail), and one protocol runs it. The sides differ in how a first touch is made: inbound publishes (plan, draft, post, measure), outbound targets (find, rank, act under caps, verify). Agreed 2026-11-02; the inbox merge is phase 2.
