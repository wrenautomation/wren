# Sites: every page we run, and cheap ad landers per offer (2026-10-07)

William, 10-07: "making sure the UI portal supports first class website setup for custom landers
and listicles, and other funnel steps for ads, organic, outreach, etc." Then: "not necessarily a
visual UI for now, but like the ability to see and manage landers / demos, etc." Then: "I'm going
to be leveraging lots of custom landing pages for ads, e.g. for every single type of specific
offer I make." Then: "pairing this with our autobrowse Cloudflare workflows, and Claude Code
driven UI building, feels like a good flow for me at least."

## Answer first

- **One inventory.** Sites → Pages lists every page we run: data pages, code pages built by
  Claude Code, the lander's own pages, demo videos, booking pages and client portal hosts. Each
  row has its URL, kind, owner, status, offer, funnel stage, last change and its numbers.
- **Data pages are rows, not code.** An offer plus a template (lander or listicle) makes a page.
  Its copy is a set of fields with versions. One server template renders it at the edge, so a
  new page or variant needs no code change and no deploy.
- **Wren's pages live at `wrenautomation.com/o/<slug>`.** A client's live at `<their host>/o/<slug>`.
  The portal Worker serves both.
- **Code pages are registered, not hosted by us.** Claude Code writes a static page from the kit,
  William's yes deploys it to Cloudflare Pages through autobrowse, and `wren sites add` registers
  it. The kit gives it the same tracking and form door as a data page.
- **Every page is measured the same way:** views, forms and booking clicks per page and per
  source (ad, organic, outreach), plus ad spend for ads that link to it. The funnel table reads
  source → page → form → booking.
- **Publishing is a yes.** A new page or a copy change waits in Marketing → To approve. Retire is
  direct.

## Kinds and sources

| Kind | Examples |
|---|---|
| lander | an offer's ad lander, its variants by angle or audience |
| listicle | "5 ways to ..." with ranked items |
| pitch | the lander repo's offer pages |
| demo | a firm's demo video page (`/v/<id>`) |
| booking | a booking page (`/schedule`, a client's `/book`) |
| thank-you | after a form |
| portal | a client's portal host |

| Source | Where the page is | Who changes it |
|---|---|---|
| `data` | `site_pages` + `site_page_versions` | the portal's copy form, the CLI, Claude's draft |
| `code` | a lander repo path or a standalone dir, deployed to Cloudflare | Claude Code; "Edit in code" shows the path |
| derived | demo videos (`enrichments` kind `video`), booking pages and portal hosts (`client_domains`) | their own systems; read only here |

The lander's own pages come in through `wren sites scan`, which reads the live sitemap and keeps a
`code` row per URL with its repo path. The lander stays the only owner of its code.

## Data model

- `site_pages`: `id`, `client` (null is Wren), `slug` (unique per owner), `kind`, `source`
  (data | code), `url` (code pages; data pages derive it), `repo_path`, `template` (lander |
  listicle), `offer`, `angle`, `audience`, `variant_of` (the page it was copied from), `stage`
  (reach | trust | convert), `status` (draft | live | retired), `live_version`, `draft_version`,
  `waiting_version`, `waiting_by`, `hook` (the door its forms enter, a `hooks` id), `notes`,
  `updated_at`, `updated_by`. Main database only, like `hooks`.
- `site_page_versions`: `page`, `number`, `content` (JSON: the template's fields), `origin` (offer
  | edit | ai | copy | restore), `why`, `by`, `at`. Never overwritten.
- `site_events`: `page`, `at`, `view` (random per page load), `name` (view | cta | form | book),
  `source`, `medium`, `campaign`, `content` (the utm on arrival), `ref`, `width`. No visitor id, no
  cookie, so no consent banner. Not audited (high volume).
- `site_forms`: every form post kept whole (`page`, `fields`, the touch, `entered` the door or
  why not). Audited like any table that holds leads; only `site_events` is skipped.
- Ads: an ad links to a page when its `spec.creative.link` holds the page's URL. Spend is that
  launch's `ad_days`. An ad's own arrivals are `utm_content = <ad id>`.

## Templates

Templates are TypeScript in `packages/sites/src/templates/`: a field list (label, kind, limits)
plus a render function. Niche-agnostic. The default fill reads the offer: audience, promise,
what you get, what you give, the guarantee, the price line, the booking link.

- **lander:** hero (headline, sub, CTA), proof lines, what you get, how it works, FAQ, form, CTA,
  footer.
- **listicle:** title and intro, ranked items (name, blurb, pros, cons, rating, CTA link), a
  closing CTA and form.

Sections as data, the visual editor, a section library in the Library and live preview at two
widths are **In development**.

## Serving

- The portal Worker answers `GET /o/<slug>` on `wrenautomation.com` (route `wrenautomation.com/o/*`
  in `wrangler.toml`) and on any client host it already serves. It asks Restate `Sites/serve`
  `{host, slug}` and caches the HTML at the edge for 60 seconds. A publish or retire shows within
  a minute.
- The page is rendered from the live version's fields at serve time, so a template fix reaches
  every page without a re-publish. Values are escaped; nothing is evaluated.
- `/o/__t` (beacon) and `/o/__form` (POST) on the same host go to `Sites/track` and `Sites/form`.
  `/o/__kit.js` is the kit's script. All three answer CORS `*` on any of our hosts, so a code page
  elsewhere can use them. Bodies are text/plain JSON (no preflight) or, for a form without JS,
  urlencoded (answered with a thanks page).
- A draft's preview is `/o/__preview/<id>?t=<token>` on the app host: no-store, noindex. The
  portal's CSP allows only same-origin frames, so the preview is served there, not on the apex.
- **Why `/o/` on the apex and not a subdomain:** the same domain as the ads already verified with
  Meta, no DNS change, and the lander's `/go/<channel>/<campaign>/<content>?to=/o/<slug>` short
  links work as they are. The lander never sees `/o/`, so the seam stays clean.
- **Storage: Postgres, behind the edge cache.** KV is the next step if misses ever cost: free
  reads up to 100k a day, small text values, eventually consistent, which a 60-second cache already
  is. R2 isn't needed for pages of 20 KB. Nothing new to pay for today.

## Tracking and the door

- The tracker is one small inline script: a `view` on load with the utm and referrer it arrived
  with, `cta` on a `[data-cta]` click, `book` on a booking link, `form` on submit. It keeps the
  arrival's touch in `sessionStorage` for later events and the form, like the lander.
- The form posts its fields and touch to `/o/__form`. `Sites/form` keeps the row, then enters the
  page's door (`hooks` row) through the Spine's `door` handler (ingress-private, by hook id): the
  page's own `hook`, else the owner's first `site`-preset door (speed to lead for Wren). A page
  with no door keeps its forms and says so.
- Per-client `/go/` links are **In development**; a client's ad links straight to its page with
  utm.

## The kit (code pages)

`packages/sites/kit/`: `README.md` and `head.html`. One tag in the page's `<head>`:

```html
<script src="https://wrenautomation.com/o/__kit.js" data-page="<page id>" defer></script>
```

It sends the same events as a data page to `wrenautomation.com/o/__t` (a beacon, no preflight),
wires any `<form data-wren-form>` to the door, and tags `[data-cta]` and booking links. Offer data
comes from `wren sites offers --json`. The lander repo can take the same tag on any page.

## Publish

- Save keeps a new version as the draft. Publish asks: the page shows in To approve as
  `page:<id>:<number>`. Approve makes that version live and the page `live`. Decline keeps it
  in history. A newer ask replaces the old one. Agents and the CLI ask; only a person approves.
- A client's page goes to the client's approver once client Sites ships; until then Wren approves.
- Retire takes it down at once (the URL answers 410). It stays in the list with its numbers.

## Portal

- **Sites → Pages:** the inventory. Views: All, Offer pages, Waiting, Live, Retired, Code, Demos.
  Filter by offer, kind, status, source, client. Columns: page, URL, kind, owner, status, offer,
  angle, stage, views, forms, form rate, bookings, spend, cost per form, last change.
  Bulk retire. New page (offer, template, angle, audience). Duplicate as variant.
- **Page detail:** opens the live URL; a scaled preview of the draft (data pages); the copy form;
  versions; source (repo path, "Edit in code", or the video id); numbers by day; links in (ads
  with spend, arrivals by source and campaign); its variants side by side by numbers; notes.
- **Sites → Funnel:** source → page → forms → bookings, with spend and rates, 30 days and all.
  The graph view is **In development**.
- **In development** in the UI: the visual editor and sections, Ask Claude on a section, client
  Sites (a client's own list and approver), A/B splits per page (experiments), per-client `/go/`
  links, posts and emails pointing at a page by target, a share link for a draft.

## Phase 2: splits, client Sites, /go/, scan, ads (2026-10-07)

For many landers per offer and per client.

- A/B splits. A live data page (A) is split with up to four live pages of the same owner
  (B to E): `site_splits` and `site_split_arms` (0187), even or set weights 1 to 100. The Worker
  gives a new visitor an arm by weight and a `wab` cookie (`<split8>.<label>`, path `/o/<slug>`,
  30 days, HttpOnly) that keeps them on it. Each arm caches alone at the edge; the browser gets
  `private, no-store`. Bots (the lander's list plus headless) get A, never counted in the split.
  Each view, form and booking carries the split id, checked against the arm's page. Each arm
  counts unique visits, forms, booking clicks and, on Wren's pages, won deals (a form's email
  that booked a call after it, marked won). The call (`split-call.ts`) is a beta-binomial with a
  flat prior: Beta(1 + goals, 1 + visits - goals) per arm, P(best) from `@wren/experiments`
  `pBest`. Under 100 visits on any arm: "Too early: N more visits". Past 95%: "B wins, NN%
  sure", else "B is ahead, NN% sure"; never 100%. "Make B the page" copies B's live content onto
  A as a new version and asks; the yes (To approve, or the client's) ships it and ends the split,
  a no runs it again. Ship refuses when A and B use different templates.
- Client Sites. `clientSites` in a client's workspace: its pages only (`pageRecordFor`, by
  `owner`), with Approve and Decline. Every yes and no checks the client's approver setting
  (`mayApprove`): Wren's team when it's `wren`, the client's logins when it's `client`, either
  for `either`. A bare page id from the list approves the version waiting on it. `sites.pages`
  is now installable per client.
- Serving a client's page stays at `https://<client host>/o/<slug>`. Not `/<slug>`: the
  host's root is the client's portal, so `/book`, `/api` and app paths would collide with page
  slugs, and one path keeps one Worker route, one kit and one tracker for Wren and clients alike.
- Client `/go/` links. `/go/<link>[/<campaign>[/<content>]]?to=/o/<slug>` on a client host,
  the lander's shape. Counted in `site_hops` unless the user agent is a bot, then a 302 to the
  page with utm (`content` is the post or ad id). The kit carries the utm into events, forms and
  the door's touches. `to` is only `/o/<slug>`, `/o/f/<slug>` or `/book` (the default), so it
  never leaves the host.
- `wren sites scan`. Read only. The lander repo's content YAML and Astro pages, plus the
  sitemaps of wrenautomation.com and each live client host, against the list. Prints a
  `wren sites add` line for each page not in it. `--no-fetch` skips the sitemaps.
- Ads to pages. Page detail lists each ad that links to the page: spend, Meta's clicks, the
  page's visits, forms and bookings from that ad's id, `/go/` clicks, and cost per visit, form
  and booking where there's spend. All ads summed when there's more than one.
