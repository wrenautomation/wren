# Key store (2026-10-07)

A client's own vendor keys (Stripe, Exa, YouTube, X, models, Telnyx), kept so the worker can use them and Restate never holds them.

Before this: the worker bound `keys: null`, so saving a client's key said "in development" on prod, and the key rode in `PaymentsConsole/connect` and `AccountsConsole/setVendor` inputs, which Restate journals.

## Answer first

- **Postgres, sealed.** Each key is a row in main's `client_secrets`, sealed with envelope encryption: a fresh data key per value (AES-256-GCM), wrapped for the store's X25519 public key. Only the worker holds the private key.
- **The private key is its own SSM parameter**, `/wren/prod/keystore`, read once per worker cold start with the env. Nothing new in `/wren/prod/env`.
- **The key never reaches Restate.** The browser posts it to the portal Worker (`POST /api/keys/stage`). The Worker passes it to the sign-in Lambda's function URL, which seals it and answers with a reference (`ks_…`) and the last 4. The Restate handler gets the reference, runs its usual checks and binds it.
- **Every read and write is audited** in `client_secret_events` (audited like any main table), never with the value. The sealed rows stay out of the audit log.
- **Payments connects Stripe and sends links on prod** once the infra steps below run. Sends are still gated by flags and approvals.

## Why Postgres (option b)

| | (a) SSM per client per vendor | (b) Postgres, sealed | (c) credvault |
|---|---|---|---|
| KMS calls | one per key read per Lambda instance | one per worker cold start (the keystore parameter) | one per read, plus STS per owner |
| IAM | worker needs `ssm:PutParameter`, `DeleteParameter` on a path | read one more parameter | a tagged role per owner, `sts:TagSession` |
| Audit, rotate, last 4 | SSM history + our own table anyway | SQL, one place | its file audit, not our log |
| Limits | 10k standard parameters, 40 TPS reads | none that matter | as (a) |

(b) costs nothing new and needs no write grant on SSM. KMS overage is negligible (William, 10-01), but (b) still adds no KMS calls on the hot path.

Trade: a database dump plus the private key opens every key. Dumps hold sealed values only; the private key lives in SSM, never in the database or its backups. This replaces the vendors design's "Keys never sit in Postgres" (2026-10-07, step b).

### Why a key pair, not one symmetric key

The sign-in Lambda faces the internet and loads all of `/wren/prod/env`. It only needs to seal. With a key pair it holds the public key (a plain Lambda variable, not a secret) and can't open anything. The box worker and the voice box don't read `/wren/prod/keystore`, so they can't either.

## Store

`packages/core/src/keys.ts`, schema in `keys-schema.ts`.

- `client_secrets`: `id` (`ks_` + 32 hex, the reference), `client`, `name` (`STRIPE_SECRET_KEY`, `EXA_API_KEY`, `STRIPE_WEBHOOK_SECRET`), `state` (`staged` | `live`), `kid`, `wrapped`, `sealed`, `last4`, `version`, `bound_from`, created and updated by and at. One live row per client and name.
- `client_secret_events`: `secret`, `client`, `name`, `op` (stage, bind, put, rotate, read, delete, expire, rewrap), `by`, `why`, `at`. Never a value.
- Sealing: per value a random 32-byte data key seals the value. The data key is wrapped with a key from X25519 (an ephemeral key with the store's public key, HKDF-SHA256). Both use AES-256-GCM with `client|name` as associated data, so a sealed value only opens as that client's key of that name.
- The private key: `WREN_KEYSTORE_KEY` = `k1:<base64url>`; several, comma-separated, newest first, while a rotation runs. Its public half: `WREN_KEYSTORE_PUBLIC` = `k1:<base64url>`.

API (`KeyStore`):

- `stage({client, name, value, by})`: seal and keep aside for 1 hour. `{ref, last4}`.
- `bind({ref, client, name, by})`: a staged value becomes the client's live key of that name: a new one, or the next version of the one there (same ref). Only the person who staged it, for that client and name, within the hour. Binding twice answers the same.
- `put({client, name, value, by})`: seal and make live in one go (a secret the worker gets itself, like Stripe's webhook secret).
- `rotate({ref, client, value, by})`: a new value under the same ref.
- `get({ref, client, by, why})`: the value, audited. Only the worker can (it holds the private key).
- `delete({ref, client, by})`.
- `info({ref, client})`: name, last 4, version, when. No value, no read event.
- `rewrap(db, ring)`: after adding a new private key, rewraps every data key under it. The sealed values don't change.

Staged rows past the hour are deleted on the next stage, each with an `expire` event.

## Intake

1. Browser: `POST /api/keys/stage` with `{client, name, value}`.
2. Portal Worker (`apps/portal/src/keys.ts`): a signed-in, non-demo viewer; a client's own host pins the client. It forwards to `<LAMBDA_URL>/api/keys/stage` with the edge secret and the viewer's email.
3. Sign-in Lambda (`apps/auth/lambda/keys.ts`): only from the edge, a name it knows, a value of the right shape (`sk_`/`rk_` + `live_`/`test_` for Stripe, `whsec_` for a signing secret), a person on that client (team seat in scope, or a member). Seals and stages. Answers `{ref, last4}`.
4. Browser: calls the handler with the ref (`payments/connect {keyRef, secretRef}`, `accounts/setVendor {keyRef}`).

Why the sign-in Lambda: it already has a function URL behind the edge secret, both Workers already hold that secret, and it already reads main. No new Lambda, URL, secret or IAM. The auth Worker forwards only `/api/auth/*`, so `/api/keys/*` is reachable from the portal Worker alone.

Two guards keep raw keys out of the journal:

- The portal Worker refuses a key-shaped value on the ref routes before it reaches Restate.
- The handlers' input schemas reject key-shaped values (`noRawKeys`), and take refs only (`ks_` + 32 hex).

## Handlers changed

- `PaymentsConsole/connect`: `keyRef`, `secretRef`. Binds, reads the key once to add the webhook, keeps Stripe's signing secret with `put`.
- `AccountsConsole/setVendor`: `keyRef` for an own key.
- `Payments/send`, `Payments/stripe`: read by ref, audited, inside the journaled step, never returned from it.
- `vendor_modes.key_name` and `pay_accounts.secret_name` hold the ref now, not an SSM path.
- Status and Vendors show the last 4 of a saved key.

## Vendors that now save

These said "Saving their key here is in development" only because the worker had no store. Saving works for all of them now:

- Stripe (Payments): saves and is used. Payment links go out on the client's key.
- Exa, YouTube, X, models, Telnyx: the key saves and the vendor's mode and gate read it. Their calls still go through Wren's own paths (autobrowse sites, the gateway, Wren's Telnyx account). Using the client's key in those calls is separate work.

## The env cap and the split

`/wren/prod/env` is one JSON SecureString, near SSM's 8192-character cap. The key store adds nothing to it.

Built (loader): `WREN_SSM_ENV_PARAM` takes a comma list, read in order. The first parameter must exist. A later one may be missing (skipped, named in the log). On a name in two, the first wins; a variable set on the function wins over all. `loadSsmEnv` takes an SSM client, so tests use a fake.

Built (push): `deploy/scripts/push-secrets.sh` packs into `WREN_SSM_ENV_PARTS` parameters (default 1, today's behaviour): `/wren/prod/env`, then `/wren/prod/env-2`, and so on, first fit in file order with the service account first into part 2. Part 1 stays Advanced (8192), the others go Intelligent-Tiering (Standard, $0, while under 4096). It refuses before writing anything when it doesn't fit.

Built (infra files, not applied): `aws_ssm_parameter.env_2` and `aws_ssm_parameter.keystore` (each `{}`, value ignored), read grants for the worker (both) and the sign-in Lambda (env-2 only), the comma lists on both Lambdas, `WREN_KEYSTORE_PUBLIC` on the sign-in Lambda from `var.keystore_public_key`, and the list in `box-worker.sh`.

Order matters: a Lambda running old code fails its cold start on a comma list. So the code ships first, then `tofu apply`.

## Infra steps (main session)

1. Land and push; let CI deploy the worker, the sign-in Lambda and the portal. Nothing changes yet: no private key, so saving still says in development.
2. `node scripts/keystore-key.mjs` (AWS creds of the deploy user). It writes a new private key into `/wren/prod/keystore` (refuses if one is there; `--rotate` adds a new one in front) and prints only the public key. Put that in `terraform.tfvars` as `keystore_public_key`.
3. `tofu plan` then `tofu apply` (no `-target` on the Lambda): the two parameters, the grants, the env lists, the public key on the sign-in Lambda.
4. Recycle both Lambdas (`aws lambda update-function-configuration` touch, or the next deploy) so the next cold start reads the new list.
5. Check: the Payments page shows "Connect Stripe"; connect a Stripe test key on the test client; `client_secret_events` shows stage, bind, read.
6. The split, when wanted: `WREN_SSM_ENV_PARTS=2 deploy/scripts/push-secrets.sh` (diff SSM first: it overwrites both). Recycle the Lambdas; the box picks it up on its next deploy.
7. After rotating the private key: run `rewrap` (a small script on the CLI is left), then drop the old key from `/wren/prod/keystore`.
