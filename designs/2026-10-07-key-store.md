# Key store (2026-10-07)

One store for every secret a client owns: their own vendor keys (Stripe, Exa, YouTube, X, models, Telnyx), their mailboxes' refresh tokens, and Wren's own mail apps. The worker can use them. Restate never holds them.

Before this, the worker bound `keys: null`, so saving a client's key said "in development" on prod. The key also rode in the `PaymentsConsole/connect` and `AccountsConsole/setVendor` inputs, which Restate journals. Mail access (90dfc1f8) had added a second store: SSM under `/wren/prod/owners/<client>/keys/*`, behind `WREN_KEY_STORE=ssm` and an IAM grant that was never given. This design replaces both.

## Answer first

- **Postgres, sealed.** Each secret is a row in main's `client_secrets`, sealed with envelope encryption. Every value gets a fresh data key (AES-256-GCM), which is wrapped for the store's X25519 public key. Only the worker holds the private key.
- **The private key has its own SSM parameter**, `/wren/prod/keystore`. The worker reads it once per cold start, along with the env. Nothing new goes in `/wren/prod/env`.
- **The key never reaches Restate.** The browser posts it to the portal Worker (`POST /api/keys/stage`). The Worker passes it to the sign-in Lambda's function URL, which seals it and answers with a reference (`ks_…`) and the last 4. The Restate handler gets the reference, runs its usual checks and binds it.
- **Every read and write is audited** in `client_secret_events`, which the audit log covers like any main table. A value never appears there. The sealed rows stay out of the audit log.
- **Payments connects Stripe and sends links on prod** once the infra steps below run. Sends are still gated by flags and approvals.
- **Mail tokens live here too.** A refresh token is a row under its client, and `mail_connections.token_name` holds its ref. No `/wren/prod/owners/*/keys/*` grant is needed.

## Why Postgres (option b)

| | (a) SSM per client per secret | (b) Postgres, sealed | (c) credvault |
|---|---|---|---|
| KMS calls | one per read per Lambda instance, and one per write | one per worker cold start (the keystore parameter) | one per read, plus STS per owner |
| IAM | worker needs `ssm:PutParameter` and `DeleteParameter` on `owners/*/keys/*` | read one more parameter | a tagged role per owner, `sts:TagSession` |
| Audit, rotate, last 4 | CloudTrail, plus our own table anyway | SQL, in one place | its file audit, not our log |
| Limits | 10k standard parameters; low default write rate; 100 versions kept per parameter | none that matter | as (a) |

(b) costs nothing new and needs no write grant on SSM. KMS overage is small (William, 10-01), but (b) still keeps KMS off the hot path.

The trade: a database dump plus the private key opens every key. Dumps hold sealed values only. The private key lives in SSM, never in the database or its backups. This replaces "Keys never sit in Postgres" in the vendors design (2026-10-07, step b).

### One store, not two (mail access)

Mail access stored refresh tokens in SSM, one parameter per mailbox. We moved them here because this store is cheaper and safer for that load:

- Microsoft rotates a refresh token on every refresh, so each connected mailbox writes about once an hour. On SSM that is a `PutParameter` with a KMS call, and the write rate limit is low. Here it is one row update.
- Each token read on SSM costs a KMS decrypt per Lambda instance. Here it costs nothing beyond the query, and an event says who read it and why.
- SSM needed a wildcard write grant, `owners/*/keys/*`, on the worker role. This store needs read access to one parameter.

Nothing needs moving: `WREN_KEY_STORE` was never set on prod and the grant was never applied, so no tokens exist in SSM. The code moved:

- `tokenName(provider, address)` is now a name (`MAIL_GOOGLE_<16 hex>`) under the mailbox's client. `land` uses `put` and keeps the ref. `tokenOf` reads by ref. A rotated refresh token goes back in with `rotate`, under the same ref.
- Wren's own mail apps (`MAIL_GOOGLE_CLIENT_ID`, `MAIL_GOOGLE_CLIENT_SECRET`, `MAIL_MICROSOFT_CLIENT_ID`, `MAIL_MICROSOFT_CLIENT_SECRET`) live under the client `wren`. They are read by name (`named`) and kept for an hour once both are found. Set them with `wren keys put`. The `WREN_MAIL_*` env names still win when set.
- The `WREN_KEY_STORE` setting is gone.
- The OAuth callback's code does pass through the `MailCallback` journal. It is single use, bound to the PKCE verifier and spent at once, so it opens nothing later. The refresh token it buys is never journaled.

### Why a key pair, not one symmetric key

The sign-in Lambda faces the internet and loads all of `/wren/prod/env`. It only needs to seal. With a key pair it holds the public key, a plain Lambda variable that isn't secret, and it can't open anything. The worker Lambda and the box worker run the same services, so both read `/wren/prod/keystore`. The voice box doesn't.

## Store

The code is in `packages/core/src/keys.ts`, with the schema in `keys-schema.ts` and names and shapes in `key-refs.ts`.

- `client_secrets`: `id` (`ks_` + 32 hex, the reference), `client`, `name`, `state` (`staged` or `live`), `kid`, `wrapped`, `sealed`, `last4`, `version`, `bound_from`, and who created and updated it and when. One live row per client and name.
- `client_secret_events`: `secret`, `client`, `name`, `op` (stage, bind, put, rotate, read, delete, expire, rewrap), `by`, `why`, `at`. Never a value.
- Names: a person may paste only `KEY_SHAPES` names (`STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `EXA_API_KEY`, `YOUTUBE_API_KEY`, `X_BEARER_TOKEN`, `MODEL_API_KEY`, `TELNYX_API_KEY`), each with its shape. The worker and the CLI may also keep Wren's own: mailbox tokens (`MAIL_<PROVIDER>_<16 hex>`, JSON) and the mail apps.
- Sealing: a random 32-byte data key seals each value. The data key is wrapped with a key from X25519 (an ephemeral key with the store's public key, then HKDF-SHA256). Both steps use AES-256-GCM with `client|name` as associated data, so a sealed value only opens as that client's secret of that name.
- The private key: `WREN_KEYSTORE_KEY` = `<kid>:<base64url>`. During a rotation there are several, comma-separated, newest first. Its public half is `WREN_KEYSTORE_PUBLIC` = `<kid>:<base64url>`.

API (`KeyStore`):

- `stage({client, name, value, by})`: seal and keep aside for 1 hour. Answers `{ref, last4}`.
- `bind({ref, client, name, by})`: a staged value becomes the client's live secret of that name. It is either new or the next version of the one already there (same ref). Only the person who staged it can bind it, for that client and name, within the hour. Binding twice gives the same answer.
- `put({client, name, value, by})`: seal and make live in one step, for a secret the worker gets itself (Stripe's webhook secret, a mailbox token).
- `rotate({ref, client, value, by})`: a new value under the same ref.
- `get({ref, client, by, why})` and `named({client, name, by, why})`: the value, with a read event. Only a store built with the private key can read. One built from the public key alone (the CLI) seals and binds, and its reads refuse.
- `delete({ref, client, by})`.
- `info({ref, client})`: name, last 4, version and when. No value and no read event.
- `rewrapAll(db, ring)`: once a new private key is first in the ring, rewraps every data key under it. The sealed values don't change.

Staged rows past the hour are deleted on the next stage, each with an `expire` event.

CLI: `wren keys list <client>`, `put <client> <NAME>` (the value on stdin, sealed with `WREN_KEYSTORE_PUBLIC`), `delete <client> <ref>`, and `rewrap` (needs `WREN_KEYSTORE_KEY`, so run it under `scripts/secrets.mjs run`).

## Intake

1. Browser: `POST /api/keys/stage` with `{client, name, value}` (`apps/portal/web/src/keys.ts`).
2. Portal Worker (`apps/portal/src/keys.ts`): needs a signed-in viewer who isn't the demo. A client's own host pins the client. It forwards to `<LAMBDA_URL>/api/keys/stage` with the edge secret and the viewer's email in `x-wren-viewer`.
3. Sign-in Lambda (`apps/auth/lambda/keys.ts`): only from the edge. It checks for a name a person may paste, a value of the right shape (`sk_` or `rk_` plus `live_` or `test_` for Stripe, `whsec_` for a signing secret), and a person on that client (a team seat in scope, or a member of a non-demo client). Then it seals and stages, and answers `{ref, last4}`.
4. Browser: calls the handler with the ref (`payments/connect {keyRef, secretRef}`, `accounts/setVendor {keyRef}`).

Why the sign-in Lambda: it already has a function URL behind the edge secret, both Workers already hold that secret, and it already reads main. No new Lambda, URL, secret or IAM. The auth Worker forwards only `/api/auth/*` and strips `x-wren-viewer`, so only the portal Worker can reach `/api/keys/stage`.

Two guards keep raw keys out of the journal:

- The portal Worker refuses a key-shaped value on the ref routes (`REF_ROUTES`) before it reaches Restate. This is the one that counts, because Restate journals an input before the handler's schema reads it.
- The handlers' input schemas reject key-shaped values (`noRawKeys`) and take only refs (`ks_` + 32 hex). A handler never runs on a raw key.

## Handlers changed

- `PaymentsConsole/connect`: takes `keyRef` and `secretRef`. It binds, reads the key once to add the webhook, and keeps Stripe's signing secret with `put`.
- `AccountsConsole/setVendor`: takes `keyRef` for an own key. Refusals keep their status (403 for someone else's key, 404 for one that waited too long).
- `Payments/send`, `Payments/stripe`: read by ref, audited, inside the journaled step, never returned from it.
- `MailCallback` and the mail reader: put and read mailbox tokens by ref, as above.
- `vendor_modes.key_name`, `pay_accounts.secret_name` and `mail_connections.token_name` now hold refs, not SSM paths.
- Payments status and Vendors show the last 4 of a saved key.

## Vendors that now save

These said "Saving their key here is in development" only because the worker had no store. Saving now works for all of them:

- Stripe (Payments): saved and used. Payment links go out on the client's key.
- Exa, YouTube, X, models, Telnyx: the key saves, and the vendor's mode and gate read it. Their calls still go through Wren's own paths (autobrowse sites, the gateway, Wren's Telnyx account). Using the client's key in those calls is separate work.
- Mail (Google, Microsoft): a mailbox connects once Wren's apps are set and the store is up.

## The env cap and the split

`/wren/prod/env` is one JSON SecureString, near SSM's 8192-character cap. The key store adds nothing to it.

Built (loader): `WREN_SSM_ENV_PARAM` takes a comma list, read in order. The first parameter must load. A later one may be missing or not yet readable (`ParameterNotFound`, `AccessDenied*`); it's skipped and named in the log. Any other error stops the cold start. When a name is in two parameters, the first wins, and a variable set on the function wins over all of them. `loadSsmEnv` takes an SSM client, so tests use a fake.

Built (push): `deploy/scripts/push-secrets.sh` packs into `WREN_SSM_ENV_PARTS` parameters (default 1, today's behaviour): `/wren/prod/env`, then `/wren/prod/env-2`, and so on. Each name goes into the first part it fits. Every part is written, an empty one as `{}`, so a name never lingers in two. Part 1 stays Advanced (8192). The others use Intelligent-Tiering, which stays Standard and free under 4096. It refuses before writing anything when the names don't fit, and values go through a private temp file, never argv.

Built (infra files, not applied):

- `aws_ssm_parameter.env_2` and `aws_ssm_parameter.keystore`, each `{}` with the value ignored.
- Read grants: the worker Lambda and the box role get both; the sign-in Lambda gets env-2 only.
- The comma lists: worker `env,env-2,keystore`; sign-in `env,env-2`; `box-worker.sh` `env,env-2,keystore`.
- `WREN_KEYSTORE_PUBLIC` on the sign-in Lambda, from `var.keystore_public_key`.

Order matters: a Lambda running old code fails its cold start on a comma list, so the code ships before `tofu apply`. The box script can land first, because it skips what it can't read yet.

## Infra steps (main session)

One change covers Payments, Vendors and mail. There's no `owners/*/keys/*` grant and no `WREN_KEY_STORE`; the mail access design's step 3 IAM bullets are replaced by these steps.

1. Land and push. CI deploys the worker, the box worker, the sign-in Lambda and the portal. Nothing changes yet: with no private key, saving says it isn't turned on. The box logs `env-2` and `keystore` as skipped.
2. `tofu plan`, then `tofu apply` (no `-target` on the Lambdas). It creates the two parameters, the grants (worker, box, sign-in), and the env lists.
3. `node scripts/keystore-key.mjs` with the deploy user's AWS credentials. It writes a private key into `/wren/prod/keystore` (refusing if one is there) and prints only the public key. Put that in `terraform.tfvars` as `keystore_public_key`.
4. `tofu apply` again. The sign-in Lambda gets `WREN_KEYSTORE_PUBLIC`, and the config change recycles it.
5. Recycle the worker Lambda (a config touch) and restart the box worker (`docker restart wren-worker`) so their next start reads the key.
6. Wren's mail apps, unless `WREN_MAIL_*` are set: `WREN_KEYSTORE_PUBLIC=<public key> node scripts/prod-wren.mjs keys put wren MAIL_GOOGLE_CLIENT_ID < file`, and the same for the other three names.
7. Check: Payments shows "Connect Stripe". Connect a Stripe test key on the test client. `wren keys list wren_test` shows it with its last 4, and `client_secret_events` shows stage, bind and read.
8. The split, when wanted: add `/wren/prod/env-2` to `deploy/voice/wren-voice.service` and the voice box role first. Then `WREN_SSM_ENV_PARTS=2 deploy/scripts/push-secrets.sh` (diff SSM first: it overwrites both). Recycle the Lambdas and restart the box worker.
9. Rotating the private key: `node scripts/keystore-key.mjs --rotate`, put the new public key in tfvars, apply, and recycle. Then `node scripts/secrets.mjs run /wren/prod/keystore -- 'node scripts/prod-wren.mjs keys rewrap'`, then drop the old key from `/wren/prod/keystore`.
