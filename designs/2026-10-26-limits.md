# Limits in Postgres (WA-873)

2026-10-26. William: "where are the limits stored? … not sure if env is even the right place for it." Then: "a database for wren makes sense, autobrowse should consume a json."

## Target

Every daily limit has a code default. An operator changes one in the portal or the CLI, with no deploy. Each change is audited. Pace (gaps between calls) stays separate from limits.

## Decision

- Table `limits` in main. A row overrides one code default.
  - No client: Wren-wide. It is the new default for Wren and every client.
  - A client: that client only, and only where the spend is the client's own (`scope: "client"`).
- Code keeps the default (`LimitDef`). An empty table changes nothing.
- Each run reads its limits at its start, inside `ctx.run`. A change holds from the next run.
- Writes: AccountsConsole `setLimit` (team, plus the money permission), `wren limits set|unset`. The audit trigger records who.
- Autobrowse keeps its own caps in `~/.config/autobrowse/limits.json` (WA-874). LinkedIn invites live there.

## Scope today

Every research part is shared (one pool for Wren and every client: Google, Instagram, YouTube reads, signal collectors) or Wren-only (ad library, Exa, triggers, YouTube search, groups, team). So no research limit takes a client row now. The Wren-wide row is the lever. The client column is ready for channel limits.

## Not chosen

- Env: grows without bound, needs a deploy, no audit.
- `wren_settings`: one JSON block per Wren part, no per-client row, no code default per limit.
- A CAPS_SCALE multiplier: one knob for all, no single limit to change. Removed.

## Surfaces

- Portal: Accounts > Vendors, section "Daily limits". Team reads, admin writes. Story `pages-limits` (Revamp/Account/Limits).
- CLI: `wren limits [--client]`, `wren limits set <name> <perDay> [--burst] [--client]`, `wren limits unset <name> [--client]`.
- Map card: `map/objects/platform/limits.md`.
