# Access

Living doc. Started 2026-10-05. William asked for "multi user support for everything (user separation, rbac, etc)".

## Answer first

- Today there are two kinds of login. An operator (Wren's team) can do everything for every client. A client member is an owner or a member, and owners manage people, invoices, the contract and the look. The token carries one flag, `operator`, and about 60 checks are spread over the services and the web.
- This doc adds roles on both sides, one list of permissions, and one server check that every portal route declares. The web reads the same answer. It also adds a Team page, a Changes page, and session revocation when someone is removed.
- Left out: custom roles, sharing a single record, SSO and SCIM. Add them when a client asks.

## Roles

Wren's team. Each is an `operators` row, which gains `role` and `clients`.

- `admin` can do everything. Today's operators become admins.
- `operator` works every client, or only the listed ones. They can use records, actions, approvals and loops. They can't touch money, effect handlers, installs or the team.
- `viewer` can see what the scope allows and change nothing. Use it for a contractor, an advisor, or a buyer's walkthrough.

`clients` null means all clients. A list limits the person to those clients. The id `wren` in the list stands for Wren's own apps (Pipeline, Outbound, Inbox, Money, Loops, Handlers), since Wren is client zero.

A client's people (`client_members.role`):

- `owner`: as today. Manages people, invoices, the contract and the look, and asks for components.
- `member`: uses the apps and acts in them. Doesn't manage people and doesn't see invoices.
- `viewer` (new): reads only.

The demo reads the demo client and never writes. That doesn't change.

## Permissions

There are seven, fixed in code (`PERMISSIONS` in `@wren/core/access`).

| Permission | Covers |
|---|---|
| `read` | Open apps, records and exports |
| `act` | Record actions and queue decisions: approve, drop, pause an inbox |
| `run` | Start and stop loops, and handler forms with no effect |
| `effect` | Handler forms with an effect (send, spend), the kill switch, opener stops |
| `money` | Wren's Money app and books accounts. On a client, its invoices and plan prices |
| `manage` | People and roles, the look, asking for components. Install, configure, uninstall and add-client are team-only, because pricing is William's |
| `team` | The Team page |

| Role | read | act | run | effect | money | manage | team |
|---|---|---|---|---|---|---|---|
| admin | all | yes | yes | yes | yes | yes | yes |
| operator | scope | yes | yes | | | | |
| team viewer | scope | | | | | | |
| owner | own client | yes | | | own invoices | own people, look, ask | |
| member | own client | yes | | | | | |
| client viewer | own client | | | | | | |
| demo | demo | | | | | | |

## One check

- `can(who, permission, client?)` lives in `@wren/core/access`. `who` is read fresh from the database on every portal call: the `operators` row (role, clients), or the membership row for that client. Each is one indexed read, the same reads `clientsFor` already does. The token's claim only shapes the first paint.
- Every portal route declares its permission in the routes file it already has: `DELIVERY_ROUTES`, `PORTAL_ROUTES`, `EMAIL_CONSOLE_ROUTES` and the console's list become `{route: permission}`. One wrapper in each service checks `can` before the handler runs and sets the audit actor for writes. A route with no permission fails an inventory test, like the components test.
- `clientsFor` filters a scoped team member to their clients. `pickClient` and `pickForWrite` keep their shape.
- `portalMe` returns, for each client, the permissions this login holds there. `can` in `@wren/ui/access` reads that list. Every app, page, action and handler form declares `needs`. What a login can't do is hidden, not greyed out.
- Handler forms: a handler with an effect needs `effect`, any other needs `run`. Record actions declare their own, `act` by default.
- The CLI holds the database, so it acts as admin. That doesn't change.

## Team page

The Wren app gets a `team` List record over `operators`. It shows email, role, clients, added, and last seen (the newest Better Auth session). Its actions are Invite (email, role, clients), Change role, Set clients, and Remove. Only an admin sees it. Removing or demoting the last admin is refused, the way `keepAnOwner` guards owners.

The client's Account → People adds `viewer` to its role picker. The CLI gets `wren team add|set|rm|ls` (replacing `operators add|rm|ls`), and `--role viewer` on members.

## Removing someone

Removing or demoting someone deletes their Better Auth sessions, so their next token refresh fails. A token already issued lives up to 15 minutes. The server reads the role fresh anyway, so the person is refused on their next click.

## Changes page

`audit_events` already records who changed which row and when, in main and in every client database. A `changes` record type reads it: when, who, table, row, and what changed as a field diff. An admin sees main's changes and every client's. An owner sees their own client's changes from its Account. Views are Today, People (rows written by a person, not a pipeline) and Money tables. This is the "who did that" answer, so no one has to ask in chat.

## Phases

- A1. `@wren/core/access` (permissions, matrix, `can`), the migration (`operators.role` default `admin`, `operators.clients`, the `viewer` member role), the fresh read in `clientsFor`, and unit tests that walk the whole matrix.
- A2. Routes declare permissions, plus the wrapper in each portal service and the inventory test. Integration tests:
  - a member viewer is refused a write;
  - a scoped operator can't open another client;
  - a team viewer can't call an effect handler;
  - an operator can't open Money;
  - removal refuses the next call.
- A3. Web: `portalMe` permissions, `needs` on apps, pages, actions and handlers, the Team page, `viewer` in People, the CLI.
- A4. The Changes record, with screenshots at 1360 and 390 as an admin, an owner, a member and a viewer.

## Done when

- Every portal route has a permission, and the inventory test holds.
- Prod screenshots of the same workspace as admin, operator, owner, member and viewer show only what each may do.
- Removing a team member refuses their next click.
- Gates pass, and the map cards for clients, the portal and the console say who can do what.

## Decision log

- 2026-10-05: Written. Fixed roles over custom ones: three per side covers every case we have, and a role editor is a screen nobody needs yet. The role is read fresh per call, not trusted from the token, so a removal takes effect at once without a token blocklist. Hidden over disabled: a button the login can never press is noise. Better Auth stays (WorkOS was ruled out 09-30: SSO and custom domains are paid, and users would live with them).
- 2026-10-05, A1 built: `@wren/core/access` (permissions, both role lists, `can`, `granted`, `Need` for routes), migration 0082 (`operators.role` default `admin`, so today's operators are admins; `operators.clients`; `viewer` in the member check), `whoIs` and `teamSeat` (the fresh read), and `clientsFor` honouring a scoped operator's list. The fresh read lands on the viewer as `team` in the A2 guard, not inside `clientsFor`, so it happens once per call and handlers called straight (tests, the CLI) keep acting as an admin. Members take `--role viewer` already, since the CLI and `delivery/invite` check against `MEMBER_ROLES`.
- 2026-10-05, A2 built: every portal service is `portalService` (`@wren/core/portal`): each route's need comes from its routes map, the guard reads the role fresh and refuses before the handler runs, and hands the handler the fresh role. The console's list moved to `@wren/core/console-routes`; the edge Worker's table moved to `apps/portal/src/services.ts` and takes the same maps, so a route with no need doesn't type-check, and `apps/portal/test/inventory.test.ts` holds each map to what the worker serves. A route that names no client is checked at the login's own client (delivery, reactivation), or at Wren's apps for a team login on the consoles; a client's people stay on their own client there. Two checks sit inside handlers, where the need depends on the input: a handler form with an effect needs `effect`, and Wren's Money records (`needs: "money"` on the type) and cost views need `money`. The fresh read runs outside `ctx.run`: two indexed reads per call, and journaling them would double Restate's metered entries. Changes from today: an operator can't set a client's look or install components (`manage`), only an admin can; setting roles below admin waits for the Team page (A3).
- 2026-10-05, A3 built: `portalMe` sends each client's `can` and `role`, and `team.wren` for Wren's own apps; `can` in `@wren/ui/access` checks an `Access.needs` against it. Apps and pages declare `needs` (Money `money`, Team `team`, Billing `money`, Look `manage`); actions don't: each takes its route's need from the routes maps (`permissionOf` in `apps/portal/src/services.ts`), so a button and the server can't disagree. Handler forms show with `run`, or `effect` when the handler has one; the Catalog's install and ask show with `manage`. The Team page is `console.team` over `operators` plus the newest session, with Invite, Change role, Set clients and Remove through `ConsolePortal.teamSet`/`teamRemove` (`wren:team`). Clients come as ids or a comma list, each checked; blank is every client. Sessions end on removal, a demotion, or a narrower client list, for a team seat and for a member (`delivery/remove`, a lower role on `delivery/invite`); a promotion keeps them. `wren team add|set|rm|ls` replaces `wren operators`. An admin's own client view now hides invoices and People controls only when the role lacks them, so nothing changes for today's admins.
