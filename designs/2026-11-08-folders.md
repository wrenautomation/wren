# Folders: one tree for chats, subjects and runs

WA-1191. William 11-08: option B. "Minimize sources of truth, maximize consistency and atomicity."

## Goal

One folder tree for all the work an agent and William do together: Weaver chats, Vireo chats, Vireo subjects, Weaver runs. Claude, ChatGPT and Gemini call this Projects. A folder "Plumbers" holds the research chat, the run it made, and the copy subjects it seeded, whatever product made them.

## Target state

- One tree in wren Postgres, schema `folders`. Two tables: `folders` (the tree) and `filed` (one row per filed item).
- An item is a link: `(kind, ref)`. Kinds: `chat` (relay session id), `subject` (Vireo subject id), `run` (Weaver run id). An item is in one folder or in none (unfiled = no row).
- Vireo and Weaver know nothing of folders. Wren's portal joins the tree with each product's own list in the browser.
- Every view shows the same tree. A list shows its own kind's items in each folder; a folder with none of them still shows, so you can file into it.
- Folders nest. Depth is at most 3.
- Every write is one transaction under one advisory lock: make, rename, move, drop, file. Drop moves the folder's items and child folders to its parent. Nothing is lost.
- Writers: the portal (FoldersConsole) and the agents (`folders` CLI in both setups, JSON out).

## Options: where the tree lives (hard to change)

| | Store | For | Against |
|---|---|---|---|
| A | wren Postgres, links by `(kind, ref)` | one place, transactions, audit triggers, backed up, the portal already reads prod | chats and runs live on the Mac; a link can point at a chat that is gone |
| B | each product keeps a `folder` field (Vireo `subjects.folder`, Weaver run meta, relay index) | each product shows its own folders offline | 3 trees that drift; a move across products is not atomic; products must know folders |
| C | the relay's local file beside `agent-sessions.jsonl` | no prod write | not atomic, not backed up, subjects (prod) foldered by a Mac file; gone when the Mac is off |
| D | A, plus move the chat index and the run index into Postgres too | real FKs for every kind | the relay and the Weaver ledger are local by design (engine, offline runs); a second copy of each index |

Priorities, in order: one source of truth per fact; atomic writes; no product coupling; cost.

**Decision: A.** One tree, one writer path, one transaction per write. D fails the first priority: it copies the chat and run indexes. B fails all three.

## Sub-choice: item integrity

| | Shape | Integrity |
|---|---|---|
| a | `kind`, `ref` text, primary key `(kind, ref)` | none in the DB; the console checks |
| b | a, plus `subject_id` generated from `ref` when kind = subject, FK to `vireo.subjects` on delete cascade | subjects: DB-enforced; chats, runs: link only |
| c | one nullable column per kind, check exactly one set | same as b, three upsert paths |

**Decision: b.** One upsert path (`on conflict (kind, ref)`), and the DB refuses a subject that does not exist. Chats and runs have no table to point at (see D). A link to a chat that is gone does not show: the join drops it.
