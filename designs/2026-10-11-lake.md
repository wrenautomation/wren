# The lake

2026-10-11. William's temp note: "Data lake + data warehouse setup (our version of databricks)".

## Decision: DuckLake on S3, synced nightly in CI

| Databricks | Ours |
|---|---|
| Delta Lake (Parquet + a log) | DuckLake: Parquet in S3, the log in a Postgres catalog |
| Unity Catalog | `wren_lake` database on the box, beside main |
| Spark | DuckDB, in the process that asks |
| Jobs | `.github/workflows/lake.yml`, nightly |
| SQL warehouse, notebooks | `wren lake sql`, `lake/models/*.sql` |

`wren lake sync` reads Wren's database and every client's and writes what changed. Each changed
table is one DuckLake snapshot. Snapshots are never expired, so the lake is all history:
`wren lake sql --at 2026-10-01T00:00:00Z "<query>"` reads any table as it was. That's what
Postgres can't do, and why we store everything (data rules: never discard).

`wren lake build` runs each `lake/models/*.sql` in name order. A model writes
`warehouse.<name>`. Two to start: loop passes per day (from `runs`) and outbound per channel per
day.

## How a sync finds what changed

Prod has 204 tables and almost none carry `updated_at`, so changes are found by row hash:

1. A table's fingerprint: rows and summed row hashes, one read in Postgres. Equal to the last
   sync's (`meta.fingerprints`): skip. Most tables, most nights.
2. Otherwise each row's key and `md5(row::text)` come over. Rows whose hash is new, and keys
   that are gone, are the diff.
3. A few: deleted from the lake by key and fetched by key, 5,000 at a time. Past 5,000 and half
   the table: the table is reloaded in one read.
4. A new Postgres column becomes a lake column. A table with no key uses the hash as its key.

Columns ending in `secret`, `password` or `token` never leave Postgres. Types DuckDB doesn't
read natively come over as text.

Layout: Wren's `public` schema is `wren.*`, its other schemas `wren_<schema>.*`, a client's
`client_<id>.*`.

## First run (2026-10-12, Wren's database, from the Mac)

264 tables, 2.4M rows, 539 MB of Parquet, none failed: 224 s. The next sync, 3 tables changed:
95 s, nearly all of it fingerprint reads.

In CI (run 38207199744, the catalog on the box across the internet): a new table costs about
4.5 s, mostly catalog round trips. A night with nothing new: about 3 to 4 minutes per database,
plus 3 minutes compacting, so about 13 minutes today. The job allows 230 and the AWS session 4 h.
The first try hit the old 55-minute cap mid-way; fingerprints now save every 50 tables, so a cut
run resumes rather than starts over.

## Where it runs

CI, not the box. The box is 4 GB and arm64; a sync of 1.8 GB holds a table's hashes in memory,
and DuckDB's native module would need its own build there. CI already reaches prod's database
(migrations) and AWS (OIDC). The role gets read and write on the lake bucket only.

The bucket: private, SSE-S3, versioned, a deleted file kept 30 days. No KMS: it bills per
request and DuckLake reads many small files.

## Not now

- Streaming changes (logical replication, Debezium). Nightly is enough for reports; a table
  that needs fresher data can sync alone (`--table`).
- A query UI. `wren lake sql` and the console's reports first.
- Client access to their own lake schema.

## Decision log

- DuckLake over Delta or Iceberg: the catalog is a Postgres database we already run, no
  metastore service, and DuckDB is already a dependency.
- Row hashes over `updated_at`: works on every table today and catches deletes.
- Never expire snapshots: storage is cheap, history isn't recoverable.
- Secrets dropped by column name: the lake is read by more tools than Postgres is.
