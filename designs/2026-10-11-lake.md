# The lake

2026-10-11. William's temp note: "Data lake + data warehouse setup (our version of databricks)".

## Decision: DuckLake on S3, synced nightly in CI

| Databricks | Ours |
|---|---|
| Delta Lake (Parquet + a log) | DuckLake: Parquet in S3, the log in a Postgres catalog |
| Unity Catalog | `wren_lake` database on the box, beside main |
| Spark | DuckDB, in the process that asks |
| Jobs | `.github/workflows/lake.yml`, nightly |
| SQL warehouse, notebooks | `wren lake sql`, `lake/models/*.sql` |

`wren lake sync` reads Wren's database and every client's and writes what changed. Each changed
table is one DuckLake snapshot. Snapshots are never expired, so the lake is all history:
`wren lake sql --at 2026-10-01T00:00:00Z "<query>"` reads any table as it was. That's what
Postgres can't do, and why we store everything (data rules: never discard).

`wren lake build` runs each `lake/models/*.sql` in name order. A model writes
`warehouse.<name>`. Two to start: loop passes per day (from `runs`) and outbound per channel per
day.

## How a sync finds what changed

Prod has 204 tables and almost none carry `updated_at`, so changes are found by row hash:

1. A table's fingerprint: rows and summed row hashes, one read in Postgres. Equal to the last
   sync's (`meta.fingerprints`): skip. Most tables, most nights.
2. Otherwise each row's key and `md5(row::text)` come over. Rows whose hash is new, and keys
   that are gone, are the diff.
3. A few: deleted from the lake by key and fetched by key, 5,000 at a time. Past 5,000 and half
   the table: the table is reloaded in one read.
4. A new Postgres column becomes a lake column. A table with no key uses the hash as its key.

Columns ending in `secret`, `password` or `token` never leave Postgres. Types DuckDB doesn't
read natively come over as text.

Layout: Wren's `public` schema is `wren.*`, its other schemas `wren_<schema>.*`, a client's
`client_<id>.*`.

## First run (2026-10-12, Wren's database, from the Mac)

264 tables, 2.4M rows, 539 MB of Parquet, none failed: 224 s. The next sync, 3 tables changed:
95 s, nearly all of it fingerprint reads.

In CI (run 38207199744, the catalog on the box across the internet): a new table costs about
4.5 s, mostly catalog round trips. A night with nothing new: about 3 to 4 minutes per database,
plus 3 minutes compacting, so about 13 minutes today. The job allows 230 and the AWS session 4 h.
The first try hit the old 55-minute cap mid-way; fingerprints now save every 50 tables, so a cut
run resumes rather than starts over.

## Where it runs

CI, not the box. The box is 4 GB and arm64; a sync of 1.8 GB holds a table's hashes in memory,
and DuckDB's native module would need its own build there. CI already reaches prod's database
(migrations) and AWS (OIDC). The role gets read and write on the lake bucket only.

The bucket: private, SSE-S3, versioned, a deleted file kept 30 days. No KMS: it bills per
request and DuckLake reads many small files.

## Not now

- Streaming changes (logical replication, Debezium). Nightly is enough for reports; a table
  that needs fresher data can sync alone (`--table`).
- A query UI. `wren lake sql` and the console's reports first.
- Client access to their own lake schema.

## Decision log

- DuckLake over Delta or Iceberg: the catalog is a Postgres database we already run, no
  metastore service, and DuckDB is already a dependency.
- Row hashes over `updated_at`: works on every table today and catches deletes.
- Never expire snapshots: storage is cheap, history isn't recoverable.
- Secrets dropped by column name: the lake is read by more tools than Postgres is.
- 2026-11-27: events at scale, option A (keep the lake; segments loaded once into `track.events`;
  autobrowse ledgers as models). B to D rejected for now; triggers to look again in that section.
  Cause: the nightly job failed 5 of 8 nights on a 19-min `autotrack_acts` that re-read all history.

## autotrack's bucket (2026-10-13)

The autotrack recorder (`wren_automation/autotrack`) ships what a person does on a computer to a
private S3 bucket: `<device>/<session>/<segment>/events.jsonl.gz`, and labels in
`labels/<device>/<session>.json`. Its design: `autotrack/designs/2026-10-13-autotrack.md`, "Signal".

Three models read it in place, no sync step (DuckDB reads the gzipped JSONL from S3):
`autotrack_acts` (one row per click, drag, scroll, text and key; joined to the browser extension's
click, Wren's own portal command, and the labels' intent and rule signals), `autotrack_daily` (per
device and day: active minutes, time by app and domain, dead, rage, error and correction rates),
`autotrack_episodes` (one row per labelled goal).

- A model headed `-- needs: track` is built only when `WREN_LAKE_TRACK_PATH` is set (a bucket
  `s3://…/` or a directory); else `wren lake build` says it skipped it. It reads `track.events`
  (loaded once per segment, section "Events at scale") and `{{track_labels}}`, which becomes
  `read_json` over the bucket (`apps/cli/src/lake-track.ts`): declared columns, so a kind without
  a field is NULL; no files yet gives empty tables.
- No labels is fine: acts load with NULL intent and signals. Unlabelled acts stay out of the rates.
- `ci_lake` gets `s3:ListBucket` and `s3:GetObject` on the bucket (`lake.tf`); the repo secret
  `WREN_LAKE_TRACK_PATH` (production environment) feeds the build step.
- Logs are public: the build prints model names and times only, never a device or a row.
- Times are UTC. An act's time is its span: the gap to the next act, capped at 30 s. A browser
  act's `domain` is its matched web click's, else the latest web event in the last 30 s (browsers only).
- Cost: was each build reading every segment's events, all history. Fixed 2026-11-27 (section
  "Events at scale").
- Wren's portal says what a command meant: `call` in `apps/portal/web/src/api.ts` posts
  `{autotrack:{v:1, action, detail:{ids?, ok, error?}}}` per command (reads say nothing). The
  recorder stores it as an `app` event; the acts model ties it to the click or key up to 5 s
  before (`app_actions`).

## Events at scale (2026-11-27)

The nightly job failed 5 of 8 nights (11-19 to 11-26): `autotrack_acts` ran 377 s to 19 min, then
DuckLake said "TransactionContext Error: Failed to commit". Each build listed the whole track bucket
(123 GB, 333k objects, ~99.5% frames) and re-read every segment's events, all history.

Options (William picked A, 11-27: "sure i agree iwth A"):

| Option | For | Against |
|---|---|---|
| A. Keep the lake, tune it | $0; built and nightly; scans millions of rows in seconds | Up to a day old |
| B. ClickHouse, self-hosted | Live inserts, sub-second queries over billions of rows | Needs several GB; the box has 4 GB, Docker on the Mac 2 GB; a second store |
| C. ScyllaDB or Cassandra (wide column) | 100k+ writes a second across nodes | We write ~0.1 a second; no joins or grouping; JVM or 3 nodes; ScyllaDB closed source since 2025 |
| D. Postgres partitions for `audit_events` | Keeps the hot table small; no new tool | 2.1M rows, 859 MB, ~7k rows a day: no gain yet |

Priorities, in order: cost in $, no new service on a 4 GB box, a store that joins and groups.
Look again: ClickHouse when a dashboard needs live raw events or a table passes ~100M rows; D when
`audit_events` nears 5 GB; wide column only for per-user streams at 10k+ writes a second.

What A built:
- `track.events`: each whole segment loaded once, partitioned by device and day; `track.segments`
  lists what is loaded (`loadTrack`, `apps/cli/src/lake-track.ts`). A segment is whole when its
  `events.jsonl.gz` exists; one still uploading waits for the next build. The listing walks
  sessions and segments with a delimiter, so frames are never listed; 16 HEADs at a time.
- `wren lake build` loads new segments first. `wren lake track [--reload]` loads alone; `--reload`
  empties the table and loads all again.
- The DuckDB secret and the segment lister take the Mac's static S3 key (`s3Options`): a full load
  outlives a login token. CI keeps its 4 h role.
- Dry run on the real bucket (local catalog, from the Mac, 11-27): the first load took 17 min, once
  (43 sessions, 10,852 segments, 4.16M events, 194 MB of Parquet). Then `autotrack_acts` built in
  16 s (852,751 acts), down from 377 s to 19 min; `autotrack_daily` 0.5 s. A load with nothing new:
  2.5 s. A day adds ~250 segments, so ~25 s a night. The load commits per batch, so a failed run
  keeps what it loaded.

## autobrowse ledgers (2026-11-27)

The desk's run ledgers go to the track bucket: `ledgers/<kind>/<kind>-YYYY-MM.jsonl.gz` for
`calls`, `flows` and `engine` (autobrowse `src/runs/ledger-ship.ts`, on its 15-min disk timer; a
month file goes again when it grew). The bodies ledger stays on the Mac: it holds inputs and answers.
4–19 MB a month raw, so the models read them in place each build (`{{track_calls}}`,
`{{track_flows}}`, `{{track_engine}}`; declared columns, a half-written line dropped).

Models: `autobrowse_calls` (one row per call attempt), `autobrowse_flows` (one per flow run),
`autobrowse_engine_runs` (one per compiled-workflow run, with `step_count` and `failed_step`),
`autobrowse_site_daily` (per site and day: calls by path and failures, call p50 and p95, flow
outcomes, captchas, model tokens, engine runs by status). On the real ledgers (11-27): 77,680 calls,
12,641 flows, 3,999 runs, 887 site-days; all four build in 0.4 s.

The desk writes with the static key `mac-s3-store` (PutObject on the track bucket's objects). CI's
`ci_lake` already reads the whole bucket.
