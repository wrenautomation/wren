# Explorer: one Finder-style view for Canon, Weaver, Vireo and the map (2026-11-12, WA-1281)

William on the first sketch (a grid of topics, layers and shared-set slabs): "doesn't seem very
navigable to me … anything closer to a directory system or a visual filetree". Then: Finder's
column view and its tree view, columns by default; "a browser for everything", Orrery too; for
Weaver runs "the graph is hard to navigate … having an alternative way to navigate / see it would
be cool"; agents get "all the implicit folder / file structures underneath that it can grep";
"there are many to many relationships in business too".

## Goal

One part, **Explorer**, to find any item and see what it links to:

- Four views over one selection: **Columns** (default), **List** (a folding tree), **Gallery**
  (a grid of posters, for media) and **Map** (a fold map you click into). You keep your place
  when you switch views.
- Each item has one **home path**. The portal URL, the CLI and the export use it.
- Each product gives an **adapter** (one module). Canon, Vireo subjects and Weaver runs in v1;
  the metro map later.
- Many-to-many links show in every view (D1).
- Agents read the same tree with `wren paths` (JSON out), or `rg` an export (D3).

Sketches: the devboard canvas, project "Canon map", snapshot `canon-browse-v1` (A = Columns,
B = List).

## Facts (checked 11-12)

- **Orrery** (engine `packages/orrery`, 0.76.0 on 11-13; wren `packages/ui` pins 0.68.10, the same code)
  is the logic of a fold map. `tree`: a `FoldNode` has one `parent`, the box it is drawn in;
  `pathTo`, `openSet`, `toggle`, `reveal`. `nest`: nested layout (no wren user yet). `glide`:
  the motion between two frames. Orrery has no edges. The metro map folds a track's end into
  the outermost closed node on its path (`packages/ui/src/metro/fold.ts:111`).
- **Canon** (`packages/research/src/canon-library.ts`): `canonLibraryApi` answers `home`,
  `topic(name)` (one whole topic), `records`, `record`, `file`. A rule set has one owner topic
  and `usedBy`. A line carries its backing (His, agent, none) and `sources` (reached through
  findings and patterns). Records cite records (`knowledge_cites`). Routes need `wren:team`
  (`canon-console-routes.ts:5-10`). Agents already read Canon with `knowledge show|select|find`
  (JSON) and `rg canon/`.
- **Weaver**: the browser reads `weaver serve` at 127.0.0.1:4747 on the Mac
  (`apps/portal/web/src/modules/research/serve.ts:1-12`). No server code reaches it. A run's
  view holds flat lists: queries, hits (one hit has many queries), documents (pages, one hit
  each) and findings (one page each).
- **Vireo**: subject → batches → samples. A sample has zero parents (a seed), one, or more (a
  cross). While a batch is open, Vireo hides parents, names, changes and notes
  (`modules/variants/tree-model.ts:154-179`; the API strips them too).
- **Folders** (WA-1191, `designs/2026-11-08-folders.md`): one tree for chats, subjects and runs
  in Postgres, depth at most 3. Items can move; an unfiled item has no row. `FolderTree`
  (`packages/ui/src/folders.tsx:488`) draws it, with moves.
- `packages/browser` exists (page reads and slides), so the new part is not called a browser.
- WA-1281's call of 11-10 (`designs/2026-11-09-knowledge-repo.md`: a graph-kit view) is
  replaced: the graph becomes the Map view; Columns is the default.

## D1: the many-to-many model (hard to change)

Every product has many-to-many links: a rule set used by 10 topics, a page hit by 3 queries, a
crossed sample, a top-of-funnel piece that feeds 2 offers.

| | Model | For | Against |
|---|---|---|---|
| **A** | **One home per item, plus typed edges.** The home is where the item lives and is drawn. Edges join any two items. | One path per item; the fold stays a tree; edges lift in Map | Each product must name a home |
| B | Aliases only, made by each adapter, no edges | Least work | Map cannot draw or count the links |
| C | A DAG: an item has many parents, drawn under each | No home to name | An item has many paths, so URL, CLI and export disagree |
| D | A graph only; the tree is a query | Most general | Loses the fixed Finder shape and the fold |

Priorities, in order: one path per item; one model for every product; a simple fold; cost.

**Decision: A.**

- **The home is the product's own single parent:** a set's owner topic, a page's run, a
  finding's page, a sample's batch. No rule picks among parents. An item with no owner sits in
  a root folder (Canon's references sit under `canon/references`).
- **Edges.** `member`: the item also belongs under another parent; it shows there as an alias.
  Every other edge is a relation (`backs`, `cites`, `grew-from`, `applies`). Each edge has a
  direction and a label per direction ("Backed by" / "Backs").
- **Where edges live** is easy to change. v1: in `@wren/paths`, beside the contract. Columns,
  List and the CLI need no `lift`. When Map ships (step 4), `lift` goes into Orrery (it needs
  the fold), and the edge type moves with it. Then Orrery owns many-to-many for every map,
  the metro map included.

## How Columns shows many-to-many

1. **Alias rows.** A member edge shows the item under its other parent, with ↗ and "from
   <home>". You keep drilling there. "Show original" (⌘R, as in Finder) jumps to the home path.
2. **Relation folders.** Each relation is a folder you can open, like a Finder smart folder.
   Line ST-2 holds "Backed by (2)"; a reference holds "Backs (5)". Walk a link both ways by
   click: `ST-2 › Backed by › reel 17 › Backs › VC-3`.
3. **The preview lists every link.** Click one and the columns move to it.

The URL holds the route you clicked (`?at=`); the route resolves to its home, so no second
field is needed. The breadcrumb shows the route; Copy link gives the home path. Columns cannot
show the whole web at once; Map does.

## D2: where adapters run

| | Where | For | Against |
|---|---|---|---|
| A | All on the server, routes `paths/*` | One code path | Weaver's data is on the Mac; the server cannot reach it |
| B | All in the portal | No new routes | The CLI needs a second copy |
| C | Each product serves its own tree API | Products stay apart | Three APIs that drift |
| **D** | **One module per adapter, run where its data is** | Each reads its data the way it does today | Two hosts to test |

**Decision: D.** Canon and Vireo run on the server (routes `paths/*`, `wren:team`) and in the
CLI. Weaver runs in the browser and in the CLI on the Mac, both against `weaver serve`. Vireo's
adapter reads through Vireo's store, so its blind rules hold: no parents, names or notes of an
open batch.

## D3: agent access

| | How | For | Against |
|---|---|---|---|
| **A** | **CLI: `wren paths ls\|tree\|cat\|find <path>`**, JSON out | Live; the house shape (CLI, JSON, skill) | No `rg` over the whole tree |
| **B** | **Export: `wren paths export <path> <dir>`.** The home tree as folders; each item an `index.md` (its body); its aliases and relations in `links.json` | Plain `rg` works; each item once | A snapshot; it goes stale |
| C | A FUSE mount | Live and greppable | macFUSE kernel extension; Mac only |
| D | An MCP server | — | House rule: never MCP |

**Decision: A + B.** No symlinks: a shared item would show once per alias in `rg -L`, and a link
to an ancestor loops. Each root's export writes `.stamp`: Canon's head commit, Weaver's ledger
time, Vireo's last batch time.

What `wren paths` adds over `knowledge` and `rg canon/`: one namespace across products, the
topic view (borrowed sets under the topics that use them), and the links worked out (backs,
used by, grew from).

## D4: the path grammar (hard to change)

URLs, the CLI, exports and agent scripts all depend on it.

| Root | Home path | Ids | Rename or move |
|---|---|---|---|
| Canon | `canon/topics/<topic>/{guide,sets,checks,notes}/…`, `canon/topics/<topic>/sets/<set>/<line>`, `canon/references/<id>`, `canon/records/<type>/<id>`, `canon/files/<path>` | Topic, set and line ids are fixed (`sop-making`) | A renamed or folded topic or set is retired with `knowledge retire --into <id>`. The walk follows `into` to the live record; the item carries `was` (the path asked for). A retired record leaves its topic: its home is `canon/records/<type>/<id>`, with a `Replaced by` relation |
| Weaver | `weaver/<run>/pages/<doc>/<finding>`, `weaver/<run>/queries/<id>` (its pages as aliases) | Weaver's own ids | Never renamed |
| Vireo | `vireo/subjects/<slug>/batches/<batch id>/<sample id>`, `vireo/guides/<id>` | Database ids (not the batch number `n`) | A subject keeps its slug; a rename changes its name only |
| Folders | `folders/<folder id>/…`, each item an alias of its home | Folder ids | A folder move changes no item's home path |
| Map (later) | from the map's line, group and station ids, not the fold tree | — | — |

A relation folder is a segment after the item: `canon/topics/ui-design/sets/ui-design-states/ST-2/backed-by`.
An alias route ends at its item; it resolves to the home path. `cat`, Copy link and the export
use only home paths.

## D5: a route that crosses hosts

Folders run in the browser: a filed Weaver run must reach `weaver serve`, which the server cannot.
A filed Vireo subject lives on the server. So `folders/1/opener/batches` starts in the browser
and ends on the server.

| | How | For | Against |
|---|---|---|---|
| **A** | **Hand-off by home.** Walk here until a step's home is in a far root; send that home plus the rest of the route as one far `columns` call; read its answer back under the route asked | One round trip per route; the breadcrumb and Back stay in the folder | `across` (core) rewrites far paths; a far error needs its route mapped back |
| B | The far root as a proxy adapter, one remote call per method | No rewrite | A walk is one round trip per segment: a 5-deep route is 5 or more calls |
| C | A filed item links to its home; the route leaves `folders/` | No new code | The folder is lost: breadcrumb and Back leave it |
| D | Folders on the server | One host | A filed run breaks: the server cannot reach `weaver serve` |

**Decision: A** (`across`, `rooted` in `packages/core/src/paths.ts`). Priorities: the folder
stays the context (William files across products), then round trips, then code size. The
portal page reads Weaver and folders here and Canon and Vireo on the server; the CLI reads all
four on the Mac (`cliRoots`).

## The views

- **Columns.** One column per level, then a preview. Keys as in Finder. On a phone: one column
  at a time; back goes up one level.
- **List.** A folding tree. It shares `FoldChevron` with `FolderTree`; `FolderTree` keeps the
  moves. Fold state is Orrery's, keyed by route path, so an alias folds
  apart from its home. List and `tree` never open relation folders.
- **Gallery.** A poster grid for media levels: Canon references, Vireo samples, Weaver pages with
  a picture. It reuses `Poster` (`modules/canon/references.tsx`).
- **Map** (step 4, section "Map"). A fold map you click into, Canon first. Pick a box and the
  route moves to its path; a route opens the boxes on its path and lights its box.
- **Preview.** Each adapter draws its own. Canon's root is a folder page (what needs a look,
  shared sets, direction, records by type); it replaces the old Overview page. A topic shows a
  summary (counts, posters, Open the whole topic), not its layer page. A record or file shows
  `RecordBody` or `FileBody` (`record.tsx`) with `bare`: the frame already names it and lists its links.

### The part (`packages/ui/src/explorer.tsx`)

- One route (`?at=`) and one view (`?view=`, Columns when absent) in the URL. Rows are links.
- Data: `read.columns(route)` (one call per route: every column and the last item whole),
  `read.children(path, after)` (Show more, List folds), `read.find(q, under)`. Answers go through
  `useLoad` with the portal's scope, so a route seen before shows at once.
- Wide (the part 720 px or more): columns, or the tree or grid, at the left in one frame; the
  preview at the right when the last item is not a folder. The frame is as tall as the window;
  each column and the preview scroll inside it. Narrow: one pane, a Back row, the page scrolls.
- **Columns:** 240 px each. The strip scrolls sideways inside the frame (never the page) and
  keeps the last column in view. Beside a preview it shows whole columns only (CSS `round()`);
  the preview takes the rest. Keys: ↑ ↓ in a column, → into, ← out.
- **List:** the tree under the nearest folder above the route (so the breadcrumb, not a third
  indent, carries depth: ST-13). It shares only `FoldChevron` with `FolderTree`: Explorer's row
  is a link, `FolderTree`'s a toggle button with drag. Children start one step in; deeper levels keep that edge and
  read lighter (ST-16). Fold state is Orrery's `toggle` over the routes read so far.
- **Gallery:** the items beside the selected one (or in the open folder) as tiles. The adapter
  draws a tile (`tile`); the default is the poster, else the kind's icon and the name.
- **Preview:** the adapter's (`preview`), then every link of the item (the part draws them all,
  so many-to-many shows in every root).
- **Folder page:** a folder has no preview; the adapter may give it a page (`folderPage`), drawn
  where the preview sits (wide) or under the rows (narrow). Canon's root: what needs a look.
- **Canon's tree** (`packages/paths/src/canon-tree.ts`) reads only through a `CanonSource`: the
  index on the server (`canonSource` in `canon.ts`), or the portal's mocks (`CANON_SOURCE` in
  `mocks/data/paths.ts`). Stories and prod walk the same tree code.

## The adapter

```ts
interface Item {
  path: string;      // home path; on an alias row, the route to it
  name: string;
  kind: string;      // topic, set, line, reference, run, page, sample …
  sub?: string; count?: number; poster?: string;
  original?: string; // on an alias: the home path
  from?: string;     // on an alias: where the home sits ("from ui-design")
  was?: string;      // on a redirect: the path asked for
  mark?: string;     // a line's backing, `missing`, `retired`
  leaf?: boolean;
}
interface Link { rel: string; dir: "out" | "in"; label: string; items: Item[] }
interface Adapter {
  root: string;
  children(path: string, after?: string): Promise<{ items: Item[]; next?: string }>;
  item(path: string): Promise<Item>;  // light; resolves an alias or relation segment
  whole(path: string): Promise<Item & { body?: string; links: Link[]; data?: unknown }>;
  find(q: string, under?: string): Promise<Item[]>;
  stamp?(): Promise<Record<string, unknown>>; // what an export's `.stamp` records
}
```

The adapter reads home paths only. `walk`, `homeAt`, `childrenAt` and `wholeAt` (in
`packages/core/src/paths.ts`, `@wren/core/paths`) turn any route into homes, one segment at a
time. The contract sits in core because `@wren/ui` may import only core.

Errors, each a state in the UI and a JSON `error` in the CLI: `not-indexed` (Canon has no index
yet), `offline` (`weaver serve` does not answer), `unknown-path`, `blind` (an open batch's
hidden field).

| Root | Home tree | Member edges (aliases) | Relations |
|---|---|---|---|
| Canon | topics › layer › set › line; references; records by type; files | a set under each topic in its `usedBy` | `backs` (reference → line, across all topics: a new query), `cites` (record → record) |
| Weaver | run › pages › findings; run › queries | a page under each query that hit it | `hit-by` (page → queries), `grew-from` / `grew-into` (run → rounds) |
| Vireo | subjects › batches › samples; guides | — | `grew-from` / `grew-into` (sample → parents, children), `applies` (sample → guides), `applied-in` (guide → samples) |
| Folders | folder › items | every filed item | — |

Checks name their lines only in a comment today (`canon/topics/ui-design/checks/tells.mjs:2`),
so a `checks` relation waits until checks declare lines.

## Map (step 4, WA-1355)

The home tree as nested boxes, each link as a line between the boxes that show. Open a box: its
children grow inside it and its lines move to their real ends. Fold it: they go back in. Columns
cannot show the whole web; Map can.

### D6: lift and the edge in Orrery (hard to change)

Lift: a link whose end sits inside a closed box draws to that box. Metro does this per track
(`packages/ui/src/metro/fold.ts:112`, `foldOf`); Explorer needs it too. Kestrel's viewer and any
later map will also need it.

| | Shape | For | Against |
|---|---|---|---|
| **A** | **Pure functions beside the tree.** `FoldEdge {id, from, to, rel?}`; `lift(edges, open, parentOf, root?)` gives each edge its shown ends, the edges inside one box and the edges that leave the root; `bundle(lines)` merges lines with the same ends | Runs anywhere (server, browser, CLI); no renderer; metro keeps its per-track data; `parentOf` works on a `FoldNode` list or on paths | The caller must call lift and layout in order |
| B | A graph object: `FoldGraph {nodes, edges}` that `openSet`, `nest` and `glide` all take; `nest` hands each level its lifted edges | One object through every step | `nest` lays out one container at a time, so it cannot route a line between two containers; rejected 11-12 (one ELK call) |
| C | Lift stays in wren (graph kit or `@wren/paths`); Orrery has no edges | No engine release | Metro and Explorer each keep a lift; D1 said Orrery owns many-to-many for every map |
| D | No lift: ELK gets every hidden item, closed boxes get one port per inner end | Shows which inner item a line goes to | Every hidden item is loaded and laid out: Canon has about 1,500 lines and 1,900 sources, so each fold costs seconds |

Priorities, in order: one lift for every map (metro, Explorer, Kestrel); it runs where the adapter
runs (D2), so the server sends lines and not raw edges; the payload and layout grow with what shows,
not with what exists; least API.

**Decision: A.** `packages/orrery/src/edges.ts`:

```ts
interface FoldEdge { id: string; from: string; to: string; rel?: string }
type ParentOf = (id: string) => string | undefined;
parentIn(nodes: readonly FoldNode[]): ParentOf;
/** The outermost node on its path that is not open; the end itself when all are open; undefined outside `root`. */
liftEnd(id: string, open: ReadonlySet<string>, parentOf: ParentOf, root?: string): string | undefined;
lift<E extends FoldEdge>(edges: readonly E[], open, parentOf, root?): {
  lines: { edge: E; from: string; to: string }[];  // both ends shown, in two boxes
  inside: Map<string, E[]>;                         // both ends lift to one box
  outside: E[];                                     // an end outside `root`
};
bundle<E>(lines): { id: string; from: string; to: string; edges: E[]; rels: Record<string, number> }[];
```

`glide` and `play` also take `ms` (move, fade, shrink), so Map keeps under 300 ms (MV-9); metro
keeps 460 ms until William settles the duration conflict.

### Data

- **Core.** `Adapter.edges?(home)`: every edge with an end under `home`, between home paths, one
  direction per pair. `PathEdge` is a `FoldEdge` with `rel` required (core pins Orrery, as `@wren/ui`
  does). Canon: `member` (topic → each set in its `usedBy`), `backs` (source → line), `cites`
  (record → record), `into` (retired → live). Weaver (after Canon): `hit-by` (query → page),
  `grew-from`.
- **`mapAt(adapter, root, open)`** (core): reads every open container's children (all pages),
  drops relation folders and aliases (they become lines), reads `edges(root)`, lifts with
  `parentOf` = the path's parent, and bundles. Out: `{ boxes: Item[] with parent and open, lines,
  inside: count per box, outside: count per root }`. It runs where the adapter runs (D2): Canon on
  the server (route `paths/map`), Weaver in the browser. The server sends lines, never raw edges:
  a line carries its `count` and `rels`.
- **`lineAt(adapter, from, to, after?)`** (route `paths/line`): a picked line's edges, one page of
  50. An end is `{ path, open }`: a closed box takes every edge under it, an open box only its own.
  It reads no children, so it needs no fold.
- **Cost (11-13, `wren paths map`).** Canon edges are ~4,400 links; one read takes ~85 ms, so the
  server keeps them per database and Canon head. Local: the default fold (34 boxes, 91 lines)
  takes 260 ms and sends 27 KB; four topics open 380 ms; depth 3 (201 boxes) 1 s. With 50 edges per
  line the default fold was 460 KB: that is why lines carry none. From the Mac against prod, depth 3
  takes 28 s: each child read is a round trip, so time the route on the server, never this way.
- **The fold.** `{ depth: 2, open }`: the root and its first level open. The route opens its own
  path (`reveal`). Hand changes stay in the page, not the URL: a link names a place, not a fold.
- **Cap.** An open set past 300 boxes does not open: the box says "Too many to draw: open a smaller
  folder". Measure the ELK time on the largest Canon fold before the cap is final.

### Draw

- **Layout:** the graph kit lays the open set out in one ELK `layered` call with
  `INCLUDE_CHILDREN`, as metro does (`place.ts:276`): an open box is an ELK compound node (title bar
  on top), a closed box a leaf node sized by its name, a bundle an edge. ELK runs in its worker.
  Layouts cache by `openKey`.
- **Canvas:** `graph/map-canvas.tsx`, lazy like `Graph`: React Flow group nodes (`parentId`) for
  open boxes, a card for a closed one (name, kind icon, count, "N links inside"), a bundle as one
  line whose width grows with its count (`ribbonWidth`).
- **Glide:** Orrery's `glide` with `MAP_MARKS` (`[data-map]` on the inner div of each box; lines
  are `fresh`). It animates the inner div, never React Flow's wrapper, so the two transforms do not
  fight. First proof: one story that opens a box and plays the glide on React Flow.
