# DB design pass (2026-10-06)

William, 10-06: "make sure db is well designed. foreign keys, indexes, partitions, common views,
etc." and "should it have a clients.products row?"

Source: a read-only audit of prod on 10-06 (1.65 GB, about 28 min of query time a day). The 10-03
audit's settled items (FK indexes, compose selector, big views, Redis) stay settled.

## Answer first

- Integrity: two real links that live only in jsonb or in a churning table get columns and FKs.
  Three small tables get their missing FKs. `verifications.email` becomes NOT NULL.
- Growth: `audit_events` stops logging machine-written tables. `runs` drops empty polling ticks
  after 30 days. No table is partitioned yet: `audit_events` is the only candidate, and a review
  check flags it at 10M rows.
- Shared views: `latest_verifications` and `lead_channels` replace about 20 hand-built copies.
- Wren's own settings: there is no Wren row in `clients`. A `wren_settings` table uses the same block shape.

## Wren's settings: no `clients` row

A `clients` row means a separate database (`wren_client_<id>`), delivery's watch and billing for
it, and portal sign-in as a client. Wren's data lives in main, so a `wren` row would be a client
that isn't one: every loop over clients would need to skip it.

Instead, use `wren_settings`, with columns `component` (the component id, primary key), `settings`
(jsonb, the same block a client keeps in `clients.products[id]`), `updated_at` and `updated_by`.
One read, `settingsFor(db, client | null)`, returns the products map for a client or Wren. The
console's component page reads values through it, so a Wren-run part (`for: "wren"`) shows its
form. Configure for the `wren` pseudo-client writes there and needs `wren:manage`. Install and
uninstall stay client-only. The first user is the Reddit audience setting
(designs/2026-10-06-reddit-discovery.md).

## Changes

1. **`enrollments.lead_id`, `enrollments.candidate_id`**: FKs to `leads` and `contact_candidates`,
   indexed, backfilled from the step-0 message's `provenance->'address'`. Compose writes them.
   `enrollment_outcomes` and `reactivation/compose.ts` read the columns instead of the jsonb.
   `contact_candidates` churns by delete and insert, so the FK on `candidate_id` is
   `ON DELETE SET NULL`. Check what the churn does first; if it re-inserts the same people, keep
   the link by person instead.
2. **Missing FKs** (0 orphans): `experiment_alleles.journal_id` → `experiment_journal`;
   `hooks.client` and `workflow_saves.client` → `clients` (cascade). Index each one that has no
   leading index. Check what `sms_push_subscriptions.operator` holds before linking it to
   `operators`.
3. **`verifications.email` NOT NULL** plus `CHECK (email = lower(email))`. Drop
   `ck_verifications_attributed`. All 9 insert paths already set it; check that.
4. **`audit_events` skip list**: add `contact_points`, `lead_checks`, `findings`,
   `candidate_mints`, `check_outcomes`, `run_events`, `fills`, `site_days` and `ad_days` to
   `AUDIT_SKIPPED` (packages/db/src/audit). That cuts about 109k rows a day to about 32k.
   - Partition later, when the table reaches 10M rows or the volume is half full: by month on
     `at`, with retention by export to S3, then detach and drop.
   - A check in `apps/worker/src/review.ts` warns at 10M rows.
5. **`runs` retention**: rows for `outreach inbox` and `send tick` that are finished, older than
   30 days, and referenced by nothing are deleted by an existing daily loop. Raw SQL is in the
   audit notes below.
6. **`latest_verifications` view**: `DISTINCT ON (email)`, newest `checked_at` then `id`. It is
   backed by `(email, checked_at DESC, id DESC)`, which replaces `ix_verifications_email_checked_at`.
   The lead verification selector uses it first; it runs 4 correlated subqueries per lead, at about
   380 ms a call over 1,051 calls. Move the other 15 code sites and 4 views to it where the
   semantics match.
7. **`leads.person_id`**: FK to `people`, indexed, and backfilled from the newest
   `contact_candidates` row with a `lead_id`. The code that sets `contact_candidates.lead_id`
   sets it too. `lead_sheet` and `provenance.ts` read the column.
8. **`lead_channels` view**: one row per channel enrollment (email, text, dm) with company,
   person, state, active and first touch. `core/leads.ts` (`activeElsewhere`,
   `firstTouchElsewhere`) and `books.econ_channels` read it.
9. **Small query wins**:
   - `ix_companies_unassigned ON companies (id) WHERE niche IS NULL`.
   - In the enrich selectors, `NOT IN (SELECT document_id ...)` becomes `NOT EXISTS`.
10. **CHECKs on closed sets**: `sms_contacts.source_kind`, `events.kind`, `comments.kind`,
    `fills.kind`, `reports.kind` and `search_pages.verdict`. Read prod's distinct values first.
11. **Constraint names**: the 22 PKs and 5 FKs on Drizzle's default names become `pk_<table>` and
    `fk_<table>_<col>_<parent>`, as the rest of the schema names them.
12. **One base view per enrollment** (if time allows): fold `contact_outcomes`' `last_touch_at`
    and `outcome` into `enrollment_outcomes`, then rebuild the 11 funnel views on it, so two pages
    can't disagree.

## Not changed

- Soft references stay soft: provider ids, trace ids, `auth.*`, offer and template ids,
  polymorphic `subject`/`ref`/`place`, and actor `*_by` columns.
- 167 unused indexes, 21 MB in all, stay under the FK-index rule.
- `leads.company_id` stays nullable until every import path sets it.

## Audit notes

The `runs` retention SQL:

```sql
DELETE FROM runs r WHERE r.command IN ('outreach inbox','send tick')
  AND r.started_at < now() - interval '30 days' AND r.finished_at IS NOT NULL
  AND NOT EXISTS (SELECT 1 FROM messages m WHERE r.id IN (m.run_id, m.sent_run_id))
  AND NOT EXISTS (SELECT 1 FROM thread_events t WHERE t.run_id = r.id)
  AND NOT EXISTS (SELECT 1 FROM open_events o WHERE o.run_id = r.id);
```

It must also check every other table with an FK to `runs` (list them from `pg_constraint`).
