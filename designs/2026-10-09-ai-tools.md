# AI tools: a CLI and a skill, 2026-10-09

Audit item (product-audit.md, "MCP server over Handlers"): Claude, agents and a client's own AI
tools drive Wren through the same doors the portal uses. Code and UI only; nothing is announced.

Built first as an MCP server; replaced the same day by a CLI and a skill (decision log).

## What

- `/api/agent` on the portal Worker, every host (app, a client's own). Plain HTTP: `GET
  /api/agent` lists the tools; `POST /api/agent/<tool>` runs one with a JSON object body and
  answers its JSON, or `{error}` with the guard's status.
- `/agent/wren.mjs` (one file, no dependencies, Node 18+) and `/agent/SKILL.md`, static from the
  portal (`apps/portal/web/public/agent/`). Account > AI tools gives the two lines that put them in
  `~/.claude/skills/wren/` and sign the CLI in. `wren login` takes the token hidden or piped and
  keeps it in `~/.config/wren/agent.json` (0600). `WREN_TOKEN` and `WREN_HOST` override it.
- A person makes an **access token** in the portal (Account → AI tools; the team's under Wren →
  AI tools). It is shown once. It acts as that login and nothing more: every tool call goes
  through the same route and guard as the portal, as that viewer, so a token never holds more
  than its person does today. Removing the person or their grant shrinks the token at once.
- A token can be pinned to one client (a person with several). On a client's own host it is
  pinned to that host's client, like a sign-in there.
- Tokens: `wren_` + 32 random bytes base64url. Main stores the SHA-256 only, with the first 9
  characters to tell them apart, a name, the email, the pin, made, last used, expires (optional),
  revoked. Last used is written at most once a minute.
- The Worker reads a token through `Tokens/check` on Restate (not a portal route, so only the
  Worker reaches it), then forwards each tool call to the portal service with that viewer.
  Operator is read fresh from `operators`.

## Tools

| Tool (CLI command) | Goes to | |
|---|---|---|
| `types` | `console/recordsTypes` | what this login can read: id, name, fields, views |
| `list` | `console/recordsList` | a type's rows: view, search, where, sort, cursor, limit (50 max) |
| `get` | `console/recordsGet` | one row with its detail and activity |
| `handlers` | `console/recordsList` on `console.handler` | the team's handlers |
| `describe` | `console/recordsGet` on `console.handler` | a handler's input schema |
| `call` | `console/call` | runs one; an effect needs `confirm` = the handler's name, as the form asks |

- A refusal keeps its status with the guard's words, so the agent reads why. A bad token is 401
  with `WWW-Authenticate: Bearer`; the CLI exits 3 on it, and the skill sends the person to log in.
- A client login sees the first three. The handler tools answer "Wren's team only" for others;
  `console/call` refuses them anyway.

## Not now

- MCP and its OAuth (claude.ai connectors). Not planned: see the decision log.
- Writes beyond handlers (record edits, approvals). To approve stays a person's click.

## Decision log

- 2026-10-09, William: skills and CLIs, not MCP. `/api/mcp` (JSON-RPC) became `/api/agent` (plain
  HTTP) with the `wren` CLI and its skill; the same six tools, guard and tokens. A CLI costs the
  agent no tool list in context, composes with the shell, and needs no OAuth. MCP OAuth dropped.

- 2026-10-09: The Worker speaks MCP itself and maps tools onto existing portal routes. One guard
  for every door; no new Lambda path and nothing an agent can do that the portal can't.
- 2026-10-09: Generic tools, not one per handler: there are hundreds, and a client's AI tool
  would choke on the list. `describe_handler` gives the schema when needed.
- 2026-10-09, built: a pinned token goes to every route as `{client, asClient: true}`, so an
  operator's pinned token sees that client as the client does. A token made in a client's Account
  is pinned there; one made on Handlers > AI tools is as wide as its operator. Tokens/check is
  public on ingress with a zod input, like `MailCallback/land`: only the Worker holds the ingress
  token. The operator check names `access_tokens.email` by hand; drizzle printed it bare, and every
  token read as an operator until the integration test caught it.
